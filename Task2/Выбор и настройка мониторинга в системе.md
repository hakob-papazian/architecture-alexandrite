# Выбор и настройка мониторинга в системе

Компания «Александрит». Технический документ: черновик технического задания на внедрение мониторинга.

## 0. Анализ системы с точки зрения мониторинга

### Что видно сейчас

Сейчас подключена только **Яндекс Метрика** на сайте онлайн-магазина. Она показывает поведение посетителей B2C: визиты, воронку до кнопки «Сделать заказ», конверсию. Остальная часть пути заказа для Метрики не видна:

| Участок пути заказа | Где происходит | Видит ли Метрика |
|---|---|---|
| INITIATED → FILE_UPLOADED → SUBMITTED | Internet Shop → Shop API → S3 | Частично: только действия в браузере. Ошибки и задержки Shop API не видны |
| Заказ партнёра через API | API user → MES API → RabbitMQ → CRM API | **Нет**: у партнёров нет браузера, нет сессии на сайте |
| SUBMITTED → PRICE_CALCULATED (расчёт 2–30 мин) | MES API, S3 | **Нет** |
| PRICE_CALCULATED → MANUFACTURING_APPROVED | RabbitMQ → CRM API → Shop DB, продавец | **Нет** |
| MANUFACTURING_APPROVED → … → SHIPPED | RabbitMQ → MES API, оператор | **Нет** |
| SHIPPED → CLOSED | CRM API, транспортная компания | **Нет** |
| Ресурсы: ВМ, PostgreSQL, RabbitMQ, S3 | Yandex Cloud | **Нет**. Есть только базовые графики консоли облака, без алертов и без связи с заказами |

### Точки, критичные для мониторинга (по C4-диаграмме)

1. **MES API** — самый нагруженный и самый критичный контейнер, и при этом он один. Через него идут:
   - расчёт стоимости (тяжёлые CPU-задачи на минуты);
   - дашборд операторов (интерактивные запросы);
   - внешний API партнёров.
   
   Все три вида нагрузки конкурируют за ресурсы одного инстанса.
2. **RabbitMQ** — единственный канал, по которому заказ партнёра попадает в CRM и по которому системы синхронизируют статусы. Если консьюмер упал или сообщение ушло в никуда, клиент этого не видит, а заказ теряется.
3. **MES DB и Shop DB** — по одному инстансу на чтение и запись. Shop DB пишут два сервиса: Shop API и CRM API.
4. **3D files storage (S3)** — источник файлов для расчёта. Его недоступность или медленное чтение останавливает расчёты.
5. **Переходы между статусами заказа.** Это не компонент, а бизнес-процесс, растянутый на три системы. Именно здесь «теряются» заказы, поэтому его нужно мониторить отдельно, бизнес-метриками.

## 1. Мотивация

### Проблема бизнеса

- **Теряются деньги.** За месяц после открытия API компания потеряла несколько крупных контрактов. Растёт число жалоб клиентов B2C на заказы, которые делаются месяцами вместо обещанных трёх недель.
- **Причина неизвестна.** Производство справляется и может выдержать двукратный рост, значит, заказы застревают в ИТ-системе. Но где именно — при расчёте стоимости, при передаче MES ↔ CRM, в ожидании оператора — сейчас определить нельзя.
- **О проблемах узнают последними.** Сигнал о сбое приходит в виде жалобы клиента, через дни или недели после сбоя. За это время такие же сбои уже затронули десятки заказов.
- **Нагрузка растёт на 100 заказов каждый месяц.** Без данных о загрузке нельзя спланировать, когда и что масштабировать. Деньги будут уходить либо на лишние серверы, либо на потерянные заказы.

### Что даст мониторинг

| Что получит компания | Как это выглядит на практике | Кому выгодно |
|---|---|---|
| **Раннее обнаружение просрочек** | Ежедневный список заказов, которые находятся в статусе дольше нормы. Продажи связываются с клиентом **до** того, как он пожалуется, и не теряют контракт | Продажи, B2B-партнёры, клиенты |
| **Ответ на вопрос «где теряются заказы»** | Дашборд времени по этапам заказа: видно, что именно (например, ожидание расчёта) занимает 80% срока | Руководство, архитектор, тимлид |
| **Быстрое восстановление после сбоев** | Алерт «нет консьюмеров очереди заказов» приходит дежурному через 5 минут, а не через неделю от клиента. Время обнаружения (MTTD) сокращается с дней до минут, время восстановления (MTTR) — с дней до часов | Все, особенно партнёры API |
| **Обоснованные решения о расходах** | Планирование мощностей на основе данных: сколько расчётов в час выдерживает текущий сервер и когда при росте на 100 заказов в месяц его не хватит | Финансы, DevOps |
| **Доказательство эффекта изменений** | После каждого улучшения (вынос расчёта в воркеры, кеш дашборда) видно, насколько ускорился путь заказа. Инвестиции в разработку можно оправдать цифрами | Продакт-менеджер, руководство |
| **Прозрачность для партнёров** | Измеримые показатели (SLA): доступность API 99,5%, расчёт цены за N минут. Их можно вписать в договоры и выполнять | Продажи B2B |
| **Безопасные релизы** | Сравнение ошибок и латентности до и после релиза, быстрое решение об откате | Команда разработки, QA |

### Стоимость и окупаемость

- **Ресурсы команды:** около 2–2,5 человеко-месяцев DevOps-инженера и по 1–2 недели каждого бэкенд-разработчика (Java, C#) на инструментирование кода. Подробно — в разделе «План действий».
- **Инфраструктура:** 1–2 небольшие ВМ (Prometheus, Grafana, Alertmanager) и диск под метрики. Это малая доля текущих затрат на облако. Метрики managed-сервисов Yandex Cloud (PostgreSQL, Object Storage) уже собираются платформой, их нужно только подключить.
- **Окупаемость:** один сохранённый крупный B2B-контракт стоит дороже всего проекта мониторинга. Компания уже потеряла несколько таких контрактов за месяц.
- **Что будет без мониторинга:** любые следующие улучшения (масштабирование, оптимизация MES) будут делаться наугад, и их эффект нельзя будет ни измерить, ни доказать.

## 2. Выбор подхода к мониторингу

Для разных частей системы используются разные подходы. Каждый из них отвечает на свой вопрос.

| Подход | Сигналы | Где применяем | Почему |
|---|---|---|---|
| **RED** (Rate, Errors, Duration) | Число запросов, ошибки, длительность | **Сервисы, обрабатывающие запросы:** Shop API, CRM API, MES API (раздельно операторский и партнёрский трафик); консьюмеры RabbitMQ (сообщения в секунду, ошибки обработки, время обработки); воркеры расчёта стоимости (расчёты в час, неуспешные расчёты, длительность расчёта) | Показывает систему глазами пользователя: сколько запросов, сколько неуспешных, как долго ждали. Это напрямую связано с жалобами |
| **USE** (Utilization, Saturation, Errors) | Загрузка, насыщенность, ошибки ресурса | **Ресурсы:** ВМ (CPU, память, диск, сеть), managed PostgreSQL (CPU, соединения, диск, блокировки), RabbitMQ (глубина очередей, память, диск, неподтверждённые сообщения), S3 (объём, ошибки), пулы потоков и соединений в приложениях | Отвечает на вопрос «почему медленно»: какой ресурс исчерпан. Особенно важен для MES API, где расчёты и дашборд делят CPU, и для одиночных БД |
| **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | RED + насыщенность | **Внешние точки входа и SLO:** публичный API партнёров, онлайн-магазин (Shop API), дашборд операторов MES | Для внешних интерфейсов нужно видеть и качество обслуживания, и запас по ёмкости в одном месте. На этих сигналах строятся SLO и договорные SLA |
| **Бизнес-метрики процесса заказа** | Заказы по статусам, время в статусе, переходы | **Весь путь заказа поперёк трёх систем** | Ни один технический подход не покажет, что заказ «завис» в статусе PRICE_CALCULATED на 2 недели, хотя все сервисы зелёные. Это главный слой для решения проблемы компании |

### Итог по слоям

```
 ┌───────────────────────────────────────────────────────────────────────┐
 │ Бизнес-слой:  заказы по статусам, время в статусе, застрявшие заказы,  │  ← главная цель
 │               время до расчёта, до подтверждения, до взятия в работу   │
 ├───────────────────────────────────────────────────────────────────────┤
 │ Внешние входы (4 золотых сигнала):  API партнёров, Shop API, MES UI     │  ← SLO/SLA
 ├───────────────────────────────────────────────────────────────────────┤
 │ Сервисы (RED):  Shop API, CRM API, MES API, консьюмеры, воркеры расчёта │
 ├───────────────────────────────────────────────────────────────────────┤
 │ Ресурсы (USE):  ВМ, PostgreSQL, RabbitMQ, S3, пулы потоков/соединений   │
 └───────────────────────────────────────────────────────────────────────┘
```

Когда срабатывает бизнес-алерт («заказ в статусе дольше нормы»), инженер спускается по слоям: какой сервис (RED) → какой ресурс (USE).

## 3. Метрики

### Соглашения

- Метрики именуются в формате Prometheus: `<система>_<объект>_<единица>`. Счётчики имеют суффикс `_total`, длительности измеряются в секундах (`_seconds`), размеры — в байтах (`_bytes`).
- **Общие ярлыки** для всех метрик приложений: `service` (shop-api, crm-api, mes-api), `instance`, `env` (dev, release, prod). Ниже они не повторяются.
- **Контроль кардинальности ярлыков.** Если у ярлыка неограниченное число значений, Prometheus разрастается и тормозит. Поэтому в ярлыки **не** выносим `order_id`, `user_id` клиентов B2C, полный URL, текст ошибки. Вместо этого:
  - `endpoint` — шаблон маршрута (`/api/orders/{id}`), а не фактический путь;
  - `status_class` (2xx, 4xx, 5xx) вместе с кодом `status` для ограниченного набора кодов;
  - пользователь как ярлык — **только** там, где пользователей ограниченное число: партнёры API (десятки) и операторы MES (десятки).
  
  Отдельные заказы и клиенты разбираются через логи и трейсы (задания 3 и 4).

### 3.1. Метрики из предложенного списка

| № | Метрика | Беру? | Зачем нужна | Ярлыки |
|---|---|---|---|---|
| 1 | **Number of requests (RPS) for all instances** | Да | Общий трафик системы. Позволяет соотнести рост нагрузки (+100 заказов в месяц, всплески от партнёров) с деградацией и планировать мощности. Резкое падение до нуля означает недоступность | `service`, `instance`, `env`. Сама метрика — сумма по сервисам из метрик 2–4 (`http_server_requests_seconds_count`), отдельно не собирается |
| 2 | **RPS for internet shop API** | Да | Трафик Shop API (RED: Rate). Обычно отражает рекламные кампании и сезонность. Нужен для масштабирования Shop API и для сопоставления с воронкой Метрики | `endpoint`, `method`, `status_class` |
| 3 | **RPS for CRM API** | Да | Нагрузка продавцов и консьюмера CRM. Рост B2B-потока сразу виден здесь | `endpoint`, `method`, `status_class` |
| 4 | **RPS for MES API** | Да, ключевая | Самый нагруженный сервис. Нужно видеть **раздельно** трафик операторов, партнёров и запросы на расчёт: от этого зависит решение, что выносить и масштабировать первым | `endpoint`, `method`, `status_class`, **`client_type`** (operator-ui, partner-api, internal) |
| 5 | **RPS for MES API per user** | Да, с ограничениями | **Для партнёров API:** кто создаёт нагрузку, кто злоупотребляет повторами расчётов, кого ограничивать квотами. Основа будущего rate limiting и разговора с партнёром. **Для операторов:** активность при работе с дашбордом, выявление «долбящих» обновлений страницы | `client_type`, `api_client_id` (идентификатор партнёра — ограниченный список), `operator_id` (для операторского трафика; операторов десятки). **Не** для клиентов B2C |
| 6 | **RPS for shop API per user** | Нет (в Prometheus) | Клиентов B2C тысячи, ярлык `user_id` взорвёт кардинальность. Поведение покупателей уже даёт Метрика, а запросы конкретного клиента ищутся в логах по `user_id`. Защита от злоупотреблений — rate limiting на балансировщике | — |
| 7 | **RPS for CRM API per user** | Нет (отдельно) | Продавцов немного, полезной информации на уровне метрик это почти не даёт. Действия продавца с заказом нужны в аудит-логе, а не в метриках | — |
| 8 | **CPU % for shop API** | Да | USE: загрузка единственного инстанса. Сигнал к масштабированию | `instance` |
| 9 | **CPU % for CRM API** | Да | То же для CRM | `instance` |
| 10 | **CPU % for MES API** | Да, ключевая | Расчёт стоимости — CPU-задача, и она идёт в том же процессе, что и дашборд операторов. Высокий CPU прямо объясняет медленную первую страницу MES. Метрика нужна для обоснования выноса расчёта в воркеры | `instance`; после выноса расчёта — `component` (api, pricing-worker) |
| 11 | **Memory utilisation for shop API** | Да | USE: утечки памяти и частые сборки мусора в JVM, риск остановки по нехватке памяти (OOM). Дополнительно — JVM heap и паузы GC | `instance`, `area` (heap, nonheap) для JVM |
| 12 | **Memory utilisation for CRM API** | Да | То же | `instance`, `area` |
| 13 | **Memory utilisation for MES API** | Да | Обработка 3D-моделей с большим числом полигонов требует много памяти, а одна тяжёлая модель может вызвать OOM всего MES. Дополнительно — managed heap и GC .NET | `instance`, `generation` (gen0/1/2/LOH) для .NET |
| 14 | **Memory utilisation for shop db instance** | Да | USE для PostgreSQL. Нехватка памяти под кеш страниц (shared buffers и page cache) означает рост чтений с диска и замедление запросов | `db_cluster`, `host` |
| 15 | **Memory utilisation for MES db instance** | Да | То же. Дашборд операторов читает много заказов, и если рабочий набор не помещается в память, страница тормозит | `db_cluster`, `host` |
| 16 | **Number of connections for shop db instance** | Да | Shop DB пишут два сервиса. Исчерпание `max_connections` или пула соединений положит и магазин, и CRM одновременно | `db_cluster`, `database`, `state` (active, idle, idle in transaction), `application_name` (shop-api, crm-api) |
| 17 | **Number of connections for MES db instance** | Да | Насыщенность БД MES. Долгие расчёты могут держать соединения | `db_cluster`, `database`, `state`, `application_name` |
| 18 | **Response time (latency) for shop API** | Да | RED: Duration. Медленное оформление заказа и загрузка файла снижают конверсию. Измеряем гистограммой, смотрим p50, p95, p99 | `endpoint`, `method`, `status_class` |
| 19 | **Response time (latency) for CRM API** | Да | Скорость работы продавцов, то есть скорость подтверждения заказов | `endpoint`, `method`, `status_class` |
| 20 | **Response time (latency) for MES API** | Да, ключевая | Медленная первая страница MES — прямая жалоба операторов. Латентность партнёрского API — основа SLA для B2B | `endpoint`, `method`, `status_class`, `client_type` |
| 21 | **Size of S3 storage** | Да | USE для хранилища: рост объёма 3D-моделей, прогноз затрат, контроль квоты бакета, обнаружение «мусорных» загрузок | `bucket`, `storage_class` |
| 22 | **Size of shop db** | Да | Рост данных, прогноз заполнения диска managed-кластера (при заполнении кластер переходит в режим только для чтения) | `db_cluster`, `database` |
| 23 | **Size of MES db** | Да | То же. Дополнительно — размер крупных таблиц (заказы, история статусов) и их индексов: от этого зависит скорость дашборда | `db_cluster`, `database`, `table` (только топ-10 таблиц) |
| 24 | **Number of HTTP 200 for each API** | Да (как часть общей метрики) | Не отдельная метрика, а срез счётчика запросов по коду. Нужна для расчёта доли успешных запросов (SLI доступности) | `service`, `endpoint`, `status` |
| 25 | **Number of HTTP 500 for each API** | Да, с алертом | RED: Errors. Доля 5xx — главный сигнал неисправности сервиса и основа SLO по ошибкам | `service`, `endpoint`, `status` (500, 502, 503, 504) |
| 26 | **Number of HTTP 4xx for each API** | Да | Рост 4xx у партнёрского API означает, что партнёры неправильно используют API, или что сломался контракт после релиза. 429 — партнёр упирается в квоту | `service`, `endpoint`, `status` (400, 401, 403, 404, 409, 422, 429), `api_client_id` для партнёрского API |
| 27 | **Number of messages in flight (RabbitMQ)** | Да, ключевая | Насыщенность канала между MES и CRM. Растущая очередь означает, что консьюмер не успевает или упал, и заказы не доходят. Это прямой индикатор проблемы «партнёры не получили заказ» | `vhost`, `queue`, `state` (ready, unacked) |
| 28 | **Number of simultaneous sessions / active users** | Да, для MES и CRM | Число одновременно работающих операторов и продавцов. Объясняет пики нагрузки на дашборд (смена у всех операторов начинается одновременно) и помогает планировать мощности | `service`, `role` (operator, seller). Для онлайн-магазина эти данные уже даёт Метрика |
| 29 | **Kb transferred (in/out) для API и S3** | Да, на уровне инфраструктуры | Загрузка и скачивание 3D-моделей — основной объём трафика. Помогает найти аномально большие модели и контролировать затраты на исходящий трафик | `service`, `direction` (in, out), `bucket` для S3 |


### 3.2. Дополнительные метрики: бизнес-процесс заказа (главные для решения проблемы)

Эти метрики не связаны с конкретным сервисом. Они описывают путь заказа поперёк систем. Источники:
- события смены статуса, публикуемые сервисами (счётчик увеличивается в момент перехода);
- периодический экспортёр SQL-запросов к Shop DB и MES DB (снимок «сколько заказов в каждом статусе и как давно»).

| Метрика | Тип | Зачем | Ярлыки |
|---|---|---|---|
| `orders_in_status` | gauge | Сколько заказов **сейчас** в каждом статусе. Видно, где накапливаются заказы: если растёт SUBMITTED, не успевает расчёт; если растёт PRICE_CALCULATED, не успевают продавцы | `status`, `channel` (b2c, b2b), `source_system` (shop, mes) |
| `order_status_transitions_total` | counter | Поток переходов между статусами. Показывает пропускную способность каждого этапа: сколько расчётов, подтверждений и взятий в работу в час | `from_status`, `to_status`, `channel`, `source_system` |
| `order_time_in_status_seconds` | histogram | **Время на каждом этапе** (наблюдается при выходе из статуса). Это главная метрика для ответа на вопрос, где теряется время. На её основе строятся SLO по этапам | `status`, `channel`, для расчёта ещё `model_complexity` (light, medium, heavy по числу полигонов) |
| `orders_stuck_total` (gauge) | gauge | Число заказов, которые находятся в статусе дольше нормы. Это прямой список под угрозой просрочки | `status`, `channel`, `age_bucket` (>1d, >3d, >7d) |
| `order_lead_time_seconds` | histogram | Полный срок SUBMITTED → SHIPPED. Сравнивается с обещанными тремя неделями | `channel` |
| `order_oldest_in_status_age_seconds` | gauge | Возраст самого старого заказа в статусе. Ловит отдельные «забытые» заказы, которые теряются в средних значениях | `status`, `channel` |
| `b2b_orders_created_total` и `b2b_orders_lost_total` | counter | Сверка: сколько заказов партнёров принял MES API и сколько из них появилось в CRM. Расхождение означает потерю на интеграции | `api_client_id` |

### 3.4. Дополнительные метрики: RabbitMQ и консьюмеры (сверх «messages in flight»)

| Метрика | Зачем | Ярлыки |
|---|---|---|
| `rabbitmq_queue_consumers` | **Ноль консьюмеров у очереди заказов означает, что заказы не обрабатываются.** Самый важный алерт интеграции | `vhost`, `queue` |
| `rabbitmq_queue_messages_published_total` / `..._delivered_total` / `..._acked_total` | Скорость входа и выхода сообщений. Если вход больше выхода, очередь растёт | `vhost`, `queue` / `exchange` |
| `rabbitmq_queue_head_message_age_seconds` (через экспортёр или расчёт) | Возраст самого старого сообщения в очереди. Длина очереди может быть небольшой, а сообщение висит часами | `queue` |

| `app_message_processing_duration_seconds` / `app_messages_processed_total` | RED для консьюмеров в CRM API и MES API: скорость и ошибки обработки | `service`, `queue`, `message_type`, `result` (ack, nack, requeue, dlq) |

### 3.5. Дополнительные метрики: насыщенность приложений и БД

| Метрика | Зачем | Ярлыки |
|---|---|---|
| Пул соединений с БД (`hikaricp_connections_active`, `_pending` для Java; аналог в Npgsql для C#) | Запросы ждут свободное соединение, хотя БД загружена слабо. Частая причина «тормозов» | `service`, `pool` |
| Пулы потоков (`tomcat_threads_busy` / `jvm_threads_live` для Java; `dotnet_threadpool_queue_length`, `dotnet_threadpool_threads_count` для C#) | Насыщенность обработчиков запросов. Особенно важно для MES, где долгие расчёты могут занимать потоки | `service` |
| GC (`jvm_gc_pause_seconds`; `dotnet_gc_pause_ratio`) | Паузы сборщика мусора как причина скачков латентности | `service`, `gc` |
| PostgreSQL: длительность запросов (`pg_stat_statements`: топ запросов по суммарному времени), блокировки (`pg_locks`), долгие транзакции, `idle in transaction`, cache hit ratio, задержка репликации (после появления реплик) | Найти конкретный тяжёлый запрос дашборда операторов, блокировки при параллельной записи Shop API и CRM API | `db_cluster`, `database`, `queryid` (только топ-N), `mode` |
| Использование диска БД и ВМ (`disk_used_percent`), IOPS, `iowait` | Переполнение диска — частая причина полной остановки | `host`, `mount`/`disk` |
| Доступность (`probe_success`, `probe_duration_seconds` от blackbox-экспортёра) | Синтетические проверки «снаружи»: открывается ли магазин, отвечает ли публичный API партнёров, открывается ли первая страница MES. Работают, даже если инструментирование сервиса не сработало | `target`, `probe` (http, tcp) |
| Срок действия TLS-сертификатов (`probe_ssl_earliest_cert_expiry`) | Просроченный сертификат публичного API означает полный отказ у всех партнёров | `target` |

## 4. Технологии

| Задача | Решение | Обоснование |
|---|---|---|
| Хранение метрик (time-series БД) | **Prometheus** на отдельной ВМ (хранение 30 дней). При росте и для долгого хранения — **VictoriaMetrics** (через remote_write), хранение 13 месяцев для сезонного сравнения | Стандарт индустрии, бесплатный, есть клиентские библиотеки для Java и .NET и готовые экспортёры для PostgreSQL и RabbitMQ. VictoriaMetrics совместима с PromQL и экономнее по диску |
| Метрики managed-сервисов Yandex Cloud (Managed PostgreSQL, Object Storage, ВМ) | **Yandex Monitoring**: метрики уже собираются платформой. Выгрузка в Prometheus через Prometheus-совместимый API экспорта Yandex Monitoring | Не нужно ставить агентов на managed-кластеры. Получаем CPU, память, диск, соединения и размер БД, а также размер бакетов S3 |
| Детальные метрики PostgreSQL | **postgres_exporter** (пользователь с ролью `pg_monitor`) с запросами к `pg_stat_statements`, `pg_stat_activity`, `pg_locks` | Платформенные метрики не показывают конкретные запросы и блокировки |
| Метрики ВМ | **node_exporter** на каждой ВМ | USE для CPU, памяти, диска, сети |
| RabbitMQ | Встроенный плагин **rabbitmq_prometheus** (порт 15692), детальные метрики по очередям (`/metrics/per-object`) | Официальный плагин, ничего дополнительно разрабатывать не нужно |
| Shop API, CRM API (Java Spring Boot) | **Spring Boot Actuator + Micrometer** (`micrometer-registry-prometheus`), эндпоинт `/actuator/prometheus` | HTTP-метрики, JVM, HikariCP и Tomcat — из коробки. Бизнес-метрики добавляются несколькими строками кода |
| MES API (C#) | **prometheus-net** (`prometheus-net.AspNetCore`) или OpenTelemetry .NET Metrics с экспортом в Prometheus. Выбор — OpenTelemetry, если в задании 3 выбираем OpenTelemetry для трейсинга | HTTP-метрики ASP.NET Core, метрики runtime (GC, пул потоков) и пользовательские метрики расчёта |
| Бизнес-метрики «снимком» (заказы по статусам, возраст) | **sql_exporter** (или запросы в postgres_exporter) раз в минуту к репликам или к основной БД с лёгкими запросами по индексу | Не требует изменений в коде MES. Работает уже в первую неделю |
| Синтетические проверки | **blackbox_exporter** | Проверка «снаружи» магазина, API партнёров, MES UI, срока TLS-сертификатов |
| Визуализация | **Grafana** | Дашборды для разных аудиторий: бизнес, дежурный, разработчики. Доступ по ролям |
| Алертинг | **Alertmanager** → Telegram или корпоративный мессенджер, email, система тикетов (Jira или YouTrack через вебхук), телефонный обзвон дежурного для критичных алертов (через вебхук к сервису обзвона) | Группировка и подавление дублей, расписание тишины, маршрутизация по критичности |
| Хранение конфигурации | Правила алертов, дашборды Grafana и конфиги Prometheus — в Git, разворачиваются из CI (provisioning) | Воспроизводимость в окружениях dev, release и prod, ревью изменений |

**Окружения.** Полный мониторинг с алертами — в prod. В release — те же метрики и дашборды без звонков дежурному: нужен для нагрузочных тестов и сравнения версий. В dev — только метрики приложений, для отладки.

## 5. План действий (черновик технического задания)

Сроки указаны ориентировочно для текущей команды: 1 DevOps, 2 Java, 1 C#.

### Этап 1. Платформа мониторинга (недели 1–2, DevOps)

2. Закрыть доступ: Prometheus и Alertmanager — только из внутренней сети. Grafana — через SSO компании, роли Viewer (бизнес) и Editor (инженеры).
3. Настроить сбор метрик из **Yandex Monitoring** (сервисный аккаунт с ролью `monitoring.viewer`): Managed PostgreSQL (Shop DB, MES DB), Object Storage (размер бакета 3D-файлов), ВМ.
4. Установить **node_exporter** на все ВМ приложений (Shop API, CRM API, MES API, RabbitMQ).

### Этап 2. Бизнес-метрики без изменения кода (неделя 2–3, DevOps + тимлид)

9. Добавить сверку B2B: число заказов, принятых MES API, против числа заказов, созданных в CRM, за последние сутки.
10. Сделать первый дашборд «**Путь заказа**» для руководства и продаж: заказы по статусам, застрявшие заказы с разбивкой по возрасту, тренд.

> Уже после этапа 2 (около 3 недель) у бизнеса появится ежедневный список застрявших заказов, а у команды — первые данные о том, где теряется время.

### Этап 3. Инструментирование приложений (недели 3–6, разработчики)

14. **Партнёрский API:** ярлык `api_client_id` на основе аутентифицированного клиента. Метрики 4xx и 429.
15. **Консьюмеры и паблишеры RabbitMQ в CRM API и MES API:** время обработки, результат (ack, nack, dlq), тип сообщения.
16. **События смены статуса** во всех трёх сервисах: `order_status_transitions_total` и `order_time_in_status_seconds` в момент перехода.
17. Метрики активных сессий операторов и продавцов.

### Этап 4. Дашборды и алерты (недели 5–7, DevOps + тимлид + продакт)

18. Дашборды Grafana:
    - **Путь заказа** (бизнес);
    - **SLO**: доступность API партнёров, латентность MES, расчёт стоимости;
    - **Сервисы RED** по каждому API;
    - **Ресурсы USE**: ВМ, PostgreSQL, RabbitMQ, S3;
    - **Расчёт стоимости в MES**;
    - **Партнёры API**: нагрузка и ошибки по клиенту.
19. Правила алертов (см. раздел 6), разбитые на уровни **critical** (звонок дежурному), **warning** (сообщение в чат и тикет) и **info** (ежедневный отчёт).

21. Для каждого критичного алерта — **runbook** (короткая инструкция «что проверить, что сделать»), ссылка на него в аннотации алерта.

### Этап 5. Процессы (с недели 6, постоянно)

22. Ввести дежурство (on-call) среди инженеров и согласовать его с руководством: на старте только рабочие часы, критичные алерты — круглосуточно.

24. Еженедельный обзор SLO и шумных алертов: каждый ложный алерт либо исправить, либо удалить.
25. Добавить проверку в процесс релиза: после деплоя в prod 30 минут сравнивать ошибки и латентность с прошлой версией, при деградации — откат.
26. Через месяц после запуска пересмотреть пороги и SLO по накопленным данным.
27. Включить метрики в Definition of Done: новый эндпоинт или новый тип сообщения без метрик не принимается.

- В Grafana для prod доступны все дашборды из пункта 18. Данные обновляются не реже раза в минуту.
- Тестовая остановка консьюмера CRM в release приводит к алерту меньше чем за 5 минут.
- Продажи получили первый отчёт о застрявших заказах.
- Документ с перечнем метрик, ярлыков и алертов хранится в репозитории вместе с конфигурацией.

## 6. Дополнительное задание: показатели насыщенности, пороги и реакция

### Почему именно эти показатели

Насыщенность — это **доля исчерпанного ресурса** или **очередь работы, которая ждёт ресурс**. Для «Александрита» критичны те ресурсы, исчерпание которых останавливает путь заказа:
- **очередь расчёта стоимости** — главный ограничитель пропускной способности;
- **очереди RabbitMQ** — канал передачи заказов;
- **соединения и диск БД** — общие для нескольких сервисов;
- **CPU и память MES API** — один инстанс на всё.

Пороги выбраны так, чтобы оставить время на реакцию до того, как пользователь заметит проблему:
- **warning** — около 70–80%: успеть запланировать работы;
- **critical** — 90% или явный отказ: реагировать немедленно.

Для очередей важна не абсолютная длина, а **тренд и время ожидания**: очередь из 50 лёгких расчётов не страшна, очередь из 5 тяжёлых по 30 минут — уже да. Через месяц после запуска пороги уточняются по фактическим данным.

### Таблица порогов и действий

| Ресурс / показатель | Warning | Critical | Почему такой порог | Действие системы и людей |
|---|---|---|---|---|
| **Очередь расчёта стоимости:** `mes_price_calculation_wait_seconds` p95 | > 15 мин в течение 15 мин | > 45 мин в течение 15 мин, или рост `queue_size` 30 мин подряд | Обычный расчёт идёт 2–3 минуты. Ожидание больше 15 минут означает, что поток заказов превысил пропускную способность | Warning: сообщение в чат команды, автоматический тикет на планирование мощностей. Critical: звонок дежурному. **Автомасштабирование:** после выноса расчёта в воркеры — добавить воркеры (группа ВМ с автомасштабированием по `queue_size`), до выноса — включить ограничение партнёрских запросов на расчёт (429) и приоритет заказов B2C |
| **Консьюмеры очереди заказов:** `rabbitmq_queue_consumers` | — | = 0 дольше 2 мин | Без консьюмера ни один заказ не дойдёт до CRM или MES | Звонок дежурному, автоматический перезапуск сервиса-консьюмера (systemd или health-check группы ВМ), сообщение в чат |
| **Глубина очередей событий заказа:** ready + unacked | Рост 10 мин подряд или > 1 000 | Возраст самого старого сообщения > 15 мин | Нормальная задержка доставки — секунды. ### Принципы реакции

- **Critical** — только то, что требует действий человека прямо сейчас. Такой алерт должен быть редким, иначе дежурный перестанет на них реагировать.
- **Warning** — автоматический тикет с владельцем и сроком, а не просто сообщение в чат, которое никто не прочитает.
- **Автоматизация в первую очередь:** перезапуск упавшего консьюмера, добавление воркеров расчёта, увеличение диска managed-БД. Человеку остаются решения, которые нельзя принять по правилу.
- **У каждого алерта есть runbook и владелец.** Алерт без действия удаляется на еженедельном обзоре.
