## 1. Анализ системы: что покрываем трейсингом и где заказ может «сломаться»

### Путь заказа по контейнерам

На C4-диаграмме у Shop API нет связи с RabbitMQ. Из этого следует важная деталь: **заказ из магазина попадает в остальную систему через общую Shop DB.**
- Shop API сохраняет заказ (SUBMITTED) в Shop DB.
- CRM API, который тоже работает с Shop DB, находит новый заказ и публикует его в RabbitMQ для MES.
- Дальше статусы ходят между CRM API и MES API через RabbitMQ.
- CRM API записывает их в Shop DB, откуда магазин показывает статус клиенту.

```
B2C:  Customer → Internet Shop → Shop API ─(S3: 3D-модель)
                                     │
                                     ▼ SUBMITTED
                                  Shop DB ◄──── CRM API ──► RabbitMQ ──► MES API ──(S3)──► расчёт цены
                                                  ▲   ▲                      │
                                                  │   └──── PRICE_CALCULATED ┘
                         Seller → CRM ────────────┘  MANUFACTURING_APPROVED ──► MES API ◄── MES ◄── Operator
                                                          ◄── STARTED / COMPLETED / PACKAGING / SHIPPED
B2B:  API user → MES API (расчёт) ──► RabbitMQ ──► CRM API (создание заказа) ──► Shop DB
```

Заказ проходит через **3 приложения, 2 БД, брокер сообщений и S3**. При этом заказ создаётся в одной системе, считается в другой, подтверждается в третьей. Ни одна система не видит весь путь целиком.

### Системы, которые покрываем трейсингом

| Контейнер | Покрываем? | Почему |
|---|---|---|
| **Shop API** (Spring Boot) | Да, обязательно | Начало пути B2C: создание заказа, загрузка 3D-модели в S3, запись SUBMITTED |
| **CRM API** (Spring Boot) | Да, обязательно | Центральный узел: забирает заказы из Shop DB, публикует и потребляет сообщения RabbitMQ, создаёт B2B-заказы, принимает подтверждение продавца, пишет статусы в Shop DB |
| **MES API** (C#) | Да, обязательно | Расчёт стоимости (самый долгий этап), партнёрский API, взятие заказа в работу, статусы производства |
| **RabbitMQ** | Да, через передачу контекста | Брокер не создаёт спаны сам. Покрываем его тем, что продюсеры и консьюмеры передают `traceparent` в заголовках сообщений. Так в трейсе видны публикация, ожидание в очереди и обработка |
| Shop DB, MES DB, S3 | Косвенно | Спаны создаёт клиент в приложении: JDBC/Npgsql, AWS SDK. Видно запросы, время и ошибки, но сами хранилища не инструментируются |
| Internet Shop, CRM, MES (фронтенды) | Этап 2 | Трейсинг в браузере (OTel Web) полезен для замера UX, но для ответа на вопрос «где заказ» достаточно бэкендов. Трафик браузеров объёмный, а данные шумные |

На схеме 1 покрываемые контейнеры обведены **красной рамкой**. Красные метки показывают, что в них дорабатывается.

### Точки, где заказ может сломаться или зависнуть

Номера соответствуют красным кружкам на [схеме 1](diagrams/01_tracing_scope.drawio).

| № | Где | Что может пойти не так | Что сейчас видно | Что покажет трейсинг |
|---|---|---|---|---|
| 1 | Internet Shop → Shop API → S3: загрузка 3D-модели | Таймаут при загрузке большого файла, ошибка S3, файл загружен, а заказ не обновлён (нет FILE_UPLOADED) | Ничего, кроме жалобы клиента | Спан загрузки с размером файла, длительностью и ошибкой |
| 2 | Shop API → **Shop DB** → CRM API | Заказ сохранён как SUBMITTED, но CRM API его не забрал: сбой фоновой задачи, ошибка в выборке, гонка. Цепочка вызовов здесь **рвётся**: контекст не проходит через базу | Ничего: заказ «просто лежит» | Ссылка (span link) между записью заказа и его подхватом в CRM. Если второго спана нет, заказ завис именно здесь |
| 3 | CRM API ↔ RabbitMQ | Публикация «новый заказ» не подтверждена брокером, сообщение без маршрута (unroutable), консьюмер статусов упал, сообщение ушло в DLQ или зациклилось в повторах | Ничего | Спаны `publish` и `process` с одинаковым `order.id`: опубликовано, но не обработано; время в очереди; ошибка обработки |
| 4 | MES API ↔ RabbitMQ | MES не получил заказ или не опубликовал PRICE_CALCULATED и статусы производства. **B2B-заказ не создался в CRM**: это и есть жалоба партнёров «не получили заказ» | Ничего | То же: разрыв между `publish` в MES и `process` в CRM |
| 5 | MES API: расчёт стоимости + чтение модели из S3 | Расчёт идёт 2–30 минут, процесс упал или был перезапущен посреди расчёта, результат не сохранён, расчёт ждёт в очереди за тяжёлыми моделями | Ничего | Отдельные спаны «ожидание в очереди расчёта» и «расчёт» с числом полигонов. Видно, где время: в ожидании или в вычислении |
| 6 | API user → MES API | Долгий синхронный запрос, таймаут у партнёра, повторный запрос, дубль заказа, ошибка валидации | Жалоба партнёра без деталей | Трейс конкретного запроса партнёра по `request_id`. Видны повторы и дубли с одним хешем модели |
| 7 | MES → MES API → MES DB | Заказ подтверждён, но не взят в работу: не виден оператору (медленный дашборд, пагинация), назначение не сохранилось | Ничего | Время между приёмом MANUFACTURING_APPROVED в MES и MANUFACTURING_STARTED. Медленные запросы дашборда к MES DB |
| 8 | CRM → CRM API → Shop DB | Продавец не подтвердил заказ или подтверждение не дошло до MES | Ничего | Время в статусе PRICE_CALCULATED. Наличие или отсутствие публикации MANUFACTURING_APPROVED |

**Вывод.** Трейсинг нужен именно на **стыках**: при передаче через БД, через RabbitMQ и при передаче долгих задач. Внутри одного сервиса проблемы обычно видны и в логах.

## 2. Данные, которые попадают в трейсинг

### 2.1. Ресурс (описание источника, одинаковое для всех спанов сервиса)

| Атрибут | Пример | Зачем |
|---|---|---|
| `service.name` | `shop-api`, `crm-api`, `mes-api` | Какой сервис |
| `service.version` | `2.14.1` (номер сборки) | Связать проблему с релизом |
| `deployment.environment` | `prod`, `release`, `dev` | Разделить окружения |
| `host.name` / `service.instance.id` | `mes-api-vm-1` | Какой инстанс (после масштабирования) |

### 2.2. Бизнес-атрибуты заказа (главное для ответа «где заказ»)

| Атрибут | Пример | Где ставится | Зачем |
|---|---|---|---|
| `order.id` | `ORD-2024-118734` | На **каждом** спане, который относится к заказу: HTTP, публикация и обработка сообщения, расчёт, запись в БД | Ключ поиска: по нему в Jaeger находятся все трейсы заказа |
| `order.status.from` / `order.status.to` | `SUBMITTED` → `PRICE_CALCULATED` | На спане смены статуса | История статусов и место остановки |
| `order.channel` | `b2c`, `b2b` | На всех спанах заказа | Разделить потоки магазина и партнёров |
| `order.partner_id` | `partner-042` (внутренний ID, не название) | Для B2B | Ответ конкретному партнёру, нагрузка по партнёру |
| `order.external_id` | ID заказа у партнёра | Для B2B, на входе в API | Поиск по номеру, который назвал партнёр |
| `order.event_id` | UUID события | На спанах публикации и обработки | Идемпотентность, поиск дублей и повторных доставок |
| `model.file_hash` | `sha256:…` (первые 16 символов) | Загрузка файла, расчёт | Поиск дублей расчёта, связь с кешем (задание 5) |
| `model.file_size_bytes`, `model.polygons`, `model.complexity` | `48 000 000`, `1 200 000`, `heavy` | Загрузка, расчёт | Объясняют длительность расчёта |
| `pricing.queue_wait_ms`, `pricing.attempt` | `540000`, `2` | Расчёт | Ожидание в очереди и повторные попытки |
| `operator.id` | внутренний ID оператора | Взятие в работу (MES) | Кто взял заказ. Без ФИО |
| `seller.id` | внутренний ID продавца | Подтверждение (CRM) | Кто подтвердил. Без ФИО |

### 2.3. Технические атрибуты (по семантическим соглашениям OpenTelemetry)

| Тип операции | Атрибуты |
|---|---|
| HTTP-сервер и HTTP-клиент | `http.request.method`, `http.route` (шаблон, без значений), `http.response.status_code`, `url.scheme`, `server.address`, `user_agent.original` (только для партнёрского API), `client.type` (`operator-ui`, `seller-ui`, `partner-api`, `shop-ui`) |
| RabbitMQ | `messaging.system=rabbitmq`, `messaging.operation` (`publish`, `receive`, `process`), `messaging.destination.name` (exchange), `messaging.rabbitmq.destination.routing_key`, `messaging.message.id`, `messaging.message.body.size`, `messaging.rabbitmq.redelivered`, результат (`ack`, `nack`, `requeue`, `dlq`) |
| PostgreSQL | `db.system=postgresql`, `db.namespace` (имя БД), `db.operation.name`, `db.collection.name` (таблица), `db.query.text` — **только нормализованный текст с плейсхолдерами**, без значений параметров |
| S3 | `rpc.service=S3`, `rpc.method` (`PutObject`, `GetObject`), `aws.s3.bucket`, `aws.s3.key` — **хеш или ID, а не исходное имя файла клиента** |
| Ошибки | Статус спана `ERROR`, событие `exception` (`exception.type`, `exception.message`, `exception.stacktrace` — только у нас внутри, без ПДн) |

### 2.4. События и связи внутри трейса

- **События спана** (span events): `order.status_changed`, `pricing.started`, `pricing.finished`, `message.published`, `message.redelivered`, `message.dead_lettered`.
- **Ссылки** (span links): связь асинхронных шагов, например «расчёт» → «запрос на расчёт», или «подхват заказа CRM API из Shop DB» → «создание заказа в Shop API». Заказ живёт неделями, поэтому один трейс на весь срок не делаем: каждый шаг — свой трейс, а связывают их `order.id` и ссылки (см. раздел 4.2).
- **Baggage** (передаётся вместе с контекстом): `order.id` и `order.channel`. Так их не нужно заново извлекать в каждом сервисе. В baggage только ID, никаких ПДн.

### 2.5. Что НЕ попадает в трейсинг

- Персональные данные клиентов: ФИО, телефон, email, адрес доставки, платёжные данные.
- Тела запросов и сообщений, содержимое 3D-моделей, исходные имена файлов.
- Токены, API-ключи партнёров, cookie, заголовки `Authorization`.
- Значения параметров SQL-запросов.

Это гарантируется дважды: правилами в коде (белый список атрибутов) и процессором фильтрации в OpenTelemetry Collector (раздел 6).

### 2.6. Обязательные спаны (минимальный набор для пути заказа)

| Сервис | Спан | Тип |
|---|---|---|
| Shop API | `POST /orders`, `PUT /orders/{id}/model` (загрузка в S3), `POST /orders/{id}/submit`, запись в Shop DB | server, client |
| CRM API | `order.pickup` (подхват SUBMITTED из Shop DB, со ссылкой на спан Shop API), `publish order.created`, `process order.price_calculated`, `POST /orders/{id}/approve`, `publish order.approved`, `process order.status_changed`, `process b2b.order.created` | server, producer, consumer, internal |
| MES API | `process order.created`, `pricing.enqueue`, `pricing.calculate` (с `model.*`), `publish order.price_calculated`, `POST /partner/v1/price`, `publish b2b.order.created`, `GET /orders` (дашборд), `POST /orders/{id}/take`, `publish order.status_changed` | server, producer, consumer, internal |

## 3. Мотивация

### Почему нужен трейсинг, если будет мониторинг (задание 2)

Мониторинг отвечает на вопрос «**сколько** заказов застряло и **на каком этапе**». Трейсинг отвечает на вопросы «**что именно** произошло с **этим** заказом» и «**почему**». Для «Александрита» второе критично:
- Партнёр звонит и спрашивает о конкретном заказе. Сейчас ответа нет, а ему нужен конкретный ответ.
- Заказ проходит через 3 приложения, 2 базы, брокер и S3, и половина передач асинхронная. Без сквозного идентификатора и связанных спанов разбор одной жалобы — это ручное сопоставление логов на разных серверах. Это часы работы, если логи вообще сохранились.
- Сообщения теряются тихо. Метрика покажет, что B2B-заказов в CRM меньше, чем в MES, но не покажет, **какие** именно заказы и **на каком шаге** потерялись. Трейсинг покажет: «опубликовано в 10:42 MES API, не обработано CRM API».
- Расчёт идёт 2–30 минут. Трейс показывает, сколько из этого времени заказ ждал в очереди, а сколько считался. Это прямое обоснование для выноса расчёта в воркеры (задание 1).

### Что даст компании

| Для кого | Эффект |
|---|---|
| Продажи и поддержка | Ответ клиенту или партнёру о статусе конкретного заказа за минуты: где он сейчас, сколько времени на каждом этапе, была ли ошибка |
| B2B-партнёры | Меньше потерянных заказов, понятная коммуникация. Это возвращает доверие и снижает риск потери следующих контрактов |
| Команда разработки | Поиск причины за минуты вместо часов. Карта реальных зависимостей сервисов. Видно, какой релиз сломал какой участок |
| Архитектор и руководство | Данные о том, где теряется время, для приоритизации инициатив (расчёт, интеграция, дашборд) |
| Операторы и продавцы | Быстрее устраняются проблемы медленного дашборда и подтверждения: видно конкретный медленный запрос |

### Метрики, на которые повлияет внедрение трейсинга

| № | Метрика | Тип | Как измеряем | Ожидаемый эффект |
|---|---|---|---|---|
| 1 | **Время на разбор инцидента с заказом (MTTR)** — от жалобы до установления причины | Техническая | Время в тикете от создания до записи «причина найдена» | Сокращение с часов или дней до 15–30 минут |
| 2 | **Доля заказов, потерянных между системами** (опубликованы, но не обработаны; созданы в MES, но не появились в CRM) | Техническая и бизнес | Order Flow Monitor и сверка (раздел 4.6), а также DLQ | Сначала метрика станет видимой. Затем, после исправления найденных причин, стремится к 0 |
| 3 | **Время ответа клиенту или партнёру на вопрос «где мой заказ»** | Бизнес | Время первого ответа в обращении | С дней до минут, в пределах одного звонка |
| 4 | **Число жалоб на «потерянные» и просроченные заказы** и **число потерянных B2B-контрактов** | Бизнес | CRM и обращения в поддержку, отчёт продаж | Снижение: о застрявших заказах узнаём раньше клиента (с доп. заданием — автоматически) |
| 5 | **Доля заказов, нарушивших SLA этапа** (расчёт, подтверждение, взятие в работу), и время до обнаружения такого нарушения (MTTD) | Техническая и бизнес | spanmetrics и Order Flow Monitor | Обнаружение за минуты, а не по жалобе. Снижение доли нарушений после устранения узких мест |

## 4. Предлагаемое решение

Схема решения: [02_tracing_solution.drawio](diagrams/02_tracing_solution.drawio) ([открыть в браузере](https://viewer.diagrams.net/?nav=1&url=https%3A%2F%2Fraw.githubusercontent.com%2Fhakob-papazian%2Farchitecture-alexandrite%2Fsprint6%2FTask3%2Fdiagrams%2F02_tracing_solution.drawio)). Новые элементы и связи выделены **красным**.

### 4.1. Технологии

| Слой | Выбор | Почему |
|---|---|---|
| Стандарт и SDK | **OpenTelemetry** (OTel): спецификация, SDK, семантические соглашения | Вендор-нейтральный стандарт. Есть зрелая поддержка Java и .NET, автоинструментирование Spring Boot, ASP.NET Core, JDBC, Npgsql, HTTP-клиентов, RabbitMQ и AWS SDK. Те же SDK дают метрики (задание 2) и связь с логами (задание 4) |
| Протокол контекста | **W3C Trace Context** (`traceparent`, `tracestate`) + W3C Baggage | Стандарт, поддерживается по умолчанию всеми SDK OTel |
| Java (Shop API, CRM API) | **OpenTelemetry Java agent** (`-javaagent`), без изменения кода для HTTP, JDBC, RabbitMQ (spring-rabbit / amqp-client), AWS SDK. Плюс OTel API для бизнес-спанов и атрибутов `order.*` | Минимальные доработки: две Java-команды подключают агент за дни |
| C# (MES API) | **OpenTelemetry .NET SDK**: `OpenTelemetry.Instrumentation.AspNetCore`, `.Http`, `Npgsql.OpenTelemetry`, AWS SDK instrumentation. Для RabbitMQ — `RabbitMQ.Client` 7.x (встроенная поддержка OTel) или ручная обёртка publish/consume с передачей заголовков. Ручные спаны расчёта стоимости | Код MES куплен вместе с исходниками, поэтому его можно дорабатывать. Ручные спаны нужны только для расчёта и бизнес-событий |
| Сбор и обработка | **OpenTelemetry Collector** (дистрибутив contrib) в режиме шлюза, 2 инстанса за внутренним балансировщиком | Единая точка приёма. Здесь удаляются ПДн, делается сэмплинг, батчинг и маршрутизация. Сервисы не знают, куда в итоге уходят данные, и бэкенд можно сменить без изменения кода |
| Бэкенд трейсов | **Jaeger v2** (collector + query + UI) | Open source, принимает OTLP. Поиск по тегам (`order.id=…`), сравнение трейсов, карта зависимостей сервисов (System Architecture). Команде не нужно учить новый язык запросов |
| Хранилище | **Yandex Managed Service for OpenSearch**, индексы `jaeger-span-*` с ротацией по дням | Managed-сервис в том же облаке без собственной эксплуатации. Поиск по тегам работает быстро. Тот же кластер можно использовать для логов (задание 4) с раздельными индексами и правами |
| Доступ к UI | **oauth2-proxy** перед Jaeger UI + корпоративный IdP (Keycloak / AD) по OIDC | В Jaeger UI нет своей аутентификации. Подробнее — в разделе 6 |

Альтернатива — **Grafana Tempo** с хранением в Object Storage: дешевле на больших объёмах и хорошо стыкуется с Grafana из задания 2. Не выбрана на старте, потому что поиск по произвольным атрибутам в TraceQL на больших периодах медленнее, а сценарий «найти все трейсы заказа за 60 дней» для нас основной. Вернуться к ней можно без изменения кода сервисов: достаточно поменять экспортёр в Collector.

### 4.2. Как связать путь заказа, который длится неделями

Заказ живёт от минут (расчёт) до недель (производство и доставка). Держать **один** трейс на весь срок нельзя: спан, открытый неделями, не завершится и потеряется при перезапуске процесса, а сэмплинг и хранение станут непредсказуемыми. Поэтому:

1. **Один трейс — один шаг процесса**, то есть одна цепочка синхронных и асинхронных операций, вызванная событием. Например:
   - «клиент нажал Сделать заказ»: Shop API → Shop DB;
   - «CRM подхватил заказ и отправил в MES»: CRM API → RabbitMQ → MES API → постановка в очередь расчёта;
   - «расчёт и публикация цены»: MES API → RabbitMQ → CRM API → Shop DB.
2. **Атрибут `order.id` на всех спанах.** Поиск `order.id=ORD-…` в Jaeger возвращает все трейсы заказа. Отсортированные по времени, они дают полный путь.
3. **Ссылки (span links)** между шагами там, где цепочка рвётся естественным образом:
   - Shop API при сохранении заказа пишет `traceparent` в новую колонку `orders.trace_context` (или в outbox-таблицу, если будет внедрён Transactional Outbox, см. задание 1). CRM API при подхвате заказа читает её и создаёт спан `order.pickup` со ссылкой на исходный.
   - Воркер расчёта создаёт спан `pricing.calculate` со ссылкой на `pricing.enqueue`. Тогда ожидание в очереди (минуты) не раздувает трейс входящего запроса.
4. **Через RabbitMQ** контекст передаётся в заголовках AMQP-сообщения (`traceparent`, `tracestate`, `baggage`). Консьюмер продолжает трейс (parent-child) для коротких операций или создаёт ссылку для долгих.

### 4.4. Сэмплинг и объёмы

- **Head-сэмплинг в сервисах:** 100%, то есть сервис отправляет все спаны. Решение о том, что сохранить, принимает Collector.
- **Tail-сэмплинг в Collector** (решение по завершённому трейсу):
  - сохранять **100%** трейсов, где есть атрибут `order.id`. Это все операции с заказами, их немного: тысячи заказов в месяц, десятки шагов у каждого;
  - сохранять **100%** трейсов с ошибкой (`status=ERROR`) или длительностью выше порога (больше 2 с для HTTP, больше 45 мин для расчёта);
  - сохранять **10%** остальных: каталог магазина, просмотры, дашборд без действий;
  - отбрасывать health-check и `/metrics`.
- **Оценка объёма:** около 3 000 заказов в месяц × ~30 шагов × ~10 спанов ≈ 1 млн спанов в месяц на заказы. Плюс 10% фонового трафика. Это единицы и десятки гигабайт в месяц, небольшой кластер OpenSearch с этим справится.

### 4.5. Как команда пользуется трейсингом

1. Обращение клиента или партнёра: «где заказ ORD-118734?».
2. Инженер поддержки открывает Jaeger UI и ищет `order.id=ORD-118734` за последние 60 дней. Для B2B можно искать по `order.external_id`.
3. Видит список трейсов по времени:
   - «создан» → «подхвачен CRM» → «опубликован в MES» → «расчёт: ожидание 3 ч 10 мин, расчёт 24 мин, heavy» → «PRICE_CALCULATED опубликован MES API» → **нет спана обработки в CRM API**.
4. Вывод: сообщение не обработано CRM. В трейсе публикации есть `messaging.message.id`, по нему в логах CRM (задание 4) находится ошибка десериализации. Затем сообщение повторно отправляется из DLQ.
5. По `trace_id` из ответа партнёрского API (`X-Request-Id`) так же находится запрос конкретного партнёра.

### 4.6. Дополнительное задание: автоматический мониторинг прохождения заказа по данным трейсинга и алертинг

Схема: [03_tracing_monitoring.drawio](diagrams/03_tracing_monitoring.drawio) ([открыть в браузере](https://viewer.diagrams.net/?nav=1&url=https%3A%2F%2Fraw.githubusercontent.com%2Fhakob-papazian%2Farchitecture-alexandrite%2Fsprint6%2FTask3%2Fdiagrams%2F03_tracing_monitoring.drawio)). Новые элементы и связи выделены **зелёным**.

Ручной поиск в Jaeger отвечает на вопрос о конкретном заказе. Но нужно, чтобы система **сама** находила зависшие и потерянные заказы. Для этого из потока спанов строятся два сигнала.

#### А. Метрики этапов из спанов (spanmetrics)

В OTel Collector включается коннектор **`spanmetrics`**. Он считает по спанам метрики RED и отправляет их в **Prometheus** (из задания 2):
- `traces_span_metrics_calls_total{service, span_name, status_code, order_channel, order_status_to}` — число операций и ошибок по этапам;
- `traces_span_metrics_duration_seconds_bucket{…}` — длительность операций: расчёт, обработка сообщения, подтверждение.

В измерения коннектора добавляются только атрибуты с ограниченным числом значений: `order.channel`, `order.status.to`, `model.complexity`, `messaging.destination.name`. Атрибут `order.id` **не** добавляется, иначе взорвётся кардинальность.

Это даёт RED по каждому шагу пути заказа без отдельного инструментирования метриками. Кроме того, из Grafana по exemplar можно перейти от точки на графике к конкретному трейсу.

#### Б. Order Flow Monitor — состояние каждого заказа

Это новый небольшой сервис на Java Spring Boot: этот стек знают два бэкенд-разработчика. У него своя БД **Order Flow DB** (PostgreSQL).

1. **Вход.** Collector через отдельный пайплайн передаёт сервису по OTLP **только спаны событий заказа**: фильтр `order.status.to` задан, или `messaging.operation` = `publish` или `process` с атрибутом `order.id`. Это малая доля трафика.
2. **Состояние.** По каждому `order.id` хранится:
   - текущий статус и время входа в него;
   - последний `trace_id`;
   - ожидаемый следующий шаг и крайний срок по SLO этапа;
   - открытые публикации, для которых ещё нет обработки (`message_id`, время публикации).
3. **Правила обнаружения** (проверка раз в минуту):

| Правило | Условие | Значит |
|---|---|---|
| Потерянное сообщение | Есть спан `publish` с `message_id`, но нет `process` с тем же `message_id` дольше 10 мин | Сообщение не дошло или не обработано (точки 3 и 4) |
| B2B-заказ не создан в CRM | MES опубликовал `b2b.order.created`, а спана создания в CRM нет дольше 10 мин | Партнёрский заказ потерян |
| Заказ не подхвачен | SUBMITTED в Shop API, а `order.pickup` в CRM нет дольше 15 мин | Разрыв через Shop DB (точка 2) |
| Зависание этапа | Время в статусе больше SLO: SUBMITTED больше 45 мин (heavy) или больше 10 мин (light/medium); PRICE_CALCULATED больше 1 рабочего дня; MANUFACTURING_APPROVED больше 1 рабочего дня; SHIPPED больше 14 дней | Заказ под угрозой просрочки |
| Повторные ошибки | Больше 3 спанов `ERROR` по одному заказу за час | Заказ «застрял» в цикле повторов |

4. **Выход:**
   - Метрики для Prometheus (`/metrics`):
     - `order_flow_stuck_orders{status, channel, age_bucket}`;
     - `order_flow_lost_messages_total{destination}`;
     - `order_flow_b2b_not_created_total{partner_id}`;
     - `order_flow_stage_breaches_total{status, channel}`;
     - `order_flow_oldest_order_age_seconds{status}`.
   - API со списком проблемных заказов: `order_id`, этап, сколько ждёт, ссылка на трейс в Jaeger.
   - Задача продавцу в CRM API по застрявшему заказу (асинхронно, через эндпоинт CRM API или сообщение). Продавец связывается с клиентом заранее.

Сервис работает как **дополнение** к сверке по данным БД из задания 2, а не вместо неё. Если спан не дошёл (например, сервис упал до экспорта), сверка по БД всё равно найдёт заказ. Если два источника расходятся, это тоже сигнал.

#### В. Алертинг

Правила в **Prometheus**, маршрутизация в **Alertmanager** (из задания 2):

| Алерт | Выражение (упрощённо) | Уровень | Куда |
|---|---|---|---|
| `OrderMessageLost` | `increase(order_flow_lost_messages_total[10m]) > 0` | critical | Дежурный (мессенджер + звонок), тикет со списком `order_id` и ссылками на трейсы |
| `B2BOrderNotCreated` | `increase(order_flow_b2b_not_created_total[15m]) > 0` | critical | Дежурный + аккаунт-менеджер партнёра |
| `OrdersStuckInStage` | `order_flow_stuck_orders{age_bucket=">1d"} > 0` | warning | Тикет и ежедневный отчёт продажам и производству |
| `OrderStageErrorRateHigh` | доля `status_code="ERROR"` в `traces_span_metrics_calls_total` по этапу > 5% за 10 мин | critical | Дежурный |
| `PricingTooSlow` | p95 `traces_span_metrics_duration_seconds{span_name="pricing.calculate"}` > 45 мин | warning | Тикет команде MES, сигнал к масштабированию воркеров |
| `TracingPipelineDown` | нет новых спанов от сервиса > 10 мин или Collector отбрасывает спаны (`otelcol_exporter_send_failed_spans`) | warning | DevOps. Без этого алерта мониторинг по трейсам может «молчать», потому что сломан |

В каждом алерте есть `order_id` (в аннотации, а не в ярлыке метрики), ссылка на трейс в Jaeger, ссылка на дашборд и runbook.

#### Г. Визуализация

Дашборд Grafana «**Путь заказа**»:
- воронка по этапам;
- время на этапе (p50 и p95);
- таблица застрявших заказов из API Order Flow Monitor со ссылками на трейсы в Jaeger;
- ошибки по этапам.

Продажи получают ежедневный отчёт о заказах под угрозой просрочки.

#### Новые элементы на схеме 3 (зелёным)

- **Контейнеры:** Order Flow Monitor, Order Flow DB, Prometheus, Alertmanager, Grafana (последние три — из задания 2, на схеме контейнеров отражены впервые).
- **Внешняя система:** каналы оповещений.
- **Роль:** продавец или руководитель как получатель отчёта.
- **Связи:**
  - Collector → Order Flow Monitor (OTLP, только события заказа);
  - Collector → Prometheus (spanmetrics);
  - Prometheus → Order Flow Monitor (scrape);
  - Prometheus → Alertmanager → оповещения;
  - Grafana → Prometheus;
  - Grafana → Jaeger (переход к трейсу);
  - Order Flow Monitor → CRM API (задача продавцу);
  - Grafana → продавец (отчёт).

## 5. Компромиссы

| Ситуация | Почему трейсинг не поможет, невозможен или дорог | Что делаем |
|---|---|---|
| **Действия людей вне системы** | Трейсинг видит операции в коде. Он не покажет, почему продавец два дня не нажимал «Подтвердить» или почему оператор не берёт заказ (мотивация «кто взял — тот получил оплату») | Время в статусе видно (Order Flow Monitor), но причину нужно решать процессом. Это инициатива I9 из задания 1 |
| **Производство и логистика** (MANUFACTURING_STARTED → SHIPPED → CLOSED) | Этапы длятся днями и неделями и происходят физически в цеху и у транспортной компании. Трейс таких этапов — просто два события с большим промежутком | Покрываем только события смены статуса. Сроки контролируем бизнес-метриками и SLA |
| **MES — купленная система** | Исходный код есть, но это чужая архитектура, и знает её мало людей (1 C#-разработчик + тимлид). Инструментирование RabbitMQ-клиента и модуля расчёта требует ручной работы и регрессионного тестирования, а при обновлении от вендора доработки придётся переносить | Начинаем с автоинструментирования .NET (ASP.NET Core, Npgsql, HttpClient): почти без изменений кода. Ручные спаны только в 2–3 местах: расчёт и publish/consume. Доработки оформляем как отдельный модуль или middleware, чтобы их было легко переносить |
| **Внешние системы**: транспортная компания, системы партнёров, S3 как сервис | Мы не можем заставить их передавать или принимать наш контекст. Внутри S3 и чужих систем трейса нет | Трейс заканчивается на нашем клиентском спане (вызов S3, ответ партнёру). Партнёру возвращаем `X-Request-Id`, чтобы он мог сослаться на запрос. Входящий `traceparent` партнёра **не** используем как родителя (раздел 6), а сохраняем как ссылку |
| **Передача через общую Shop DB** | Контекст не проходит через базу сам по себе | Колонка `trace_context` и ссылки. Это небольшая доработка, но без неё разрыв в точке 2 останется слепым пятном. Более правильное решение — Transactional Outbox и события вместо общей БД (задание 1, I6 и I14) |
| **Долгий путь заказа** | Один трейс на недели невозможен (раздел 4.2). Хранить все спаны 120 дней дорого | Трейс на шаг + `order.id` + ссылки. Отдельное долгое хранение только для спанов смены статуса |
| **Стоимость хранения и эксплуатации** | OpenSearch — один из самых дорогих компонентов. Полное хранение всех спанов (каталог, просмотры) раздуло бы объём на порядки без пользы для задачи | Tail-сэмплинг (100% заказов и ошибок, 10% остального), ротация индексов, общий кластер с логами. При росте — переход на Tempo с хранением в S3 |
| **Нагрузка на сервисы** | Агент и SDK добавляют задержку (обычно доли миллисекунды) и CPU (1–3%). MES API и так перегружен расчётами | Батчевый асинхронный экспорт, лимиты памяти. Не создаём спаны на каждую итерацию внутри расчёта: один спан на расчёт и события начала и конца. Замеряем накладные расходы на release перед prod |
| **Фронтенды** | Трейсинг в браузере даёт много шумных данных и требует отдельной защиты публичного эндпоинта приёма | Отложен на этап 2, после бэкендов |
| **Ресурсы команды** | 1 DevOps-инженер, 1 C#-разработчик. Трейсинг конкурирует с другими инициативами задания 1 | Поэтапное внедрение (раздел 7): сначала Java-сервисы (быстро, агентом), затем MES. Order Flow Monitor — после того как пошли данные. Если ресурсов нет, мониторинг из задания 2 и сверка по БД закрывают обнаружение, а трейсинг добавляет точную диагностику |
| **Неполные данные** | Если сервис упал до экспорта спана, спана не будет | Order Flow Monitor не единственный источник: сверка по БД из задания 2 остаётся. Сам тракт трейсинга мониторится (`TracingPipelineDown`) |

## 6. Безопасность

### Угрозы

1. Утечка персональных и коммерческих данных через трейсы: ПДн клиентов, данные партнёров, внутренние идентификаторы, структура системы.
2. Несанкционированный доступ к Jaeger UI, OpenSearch, Collector.
3. Подделка или засорение трейсов: отправка ложных спанов, DoS эндпоинта приёма.
4. Внедрение контекста извне: чужой `traceparent` или `baggage` в партнёрском API.

### Меры

| Область | Мера |
|---|---|
| **Аутентификация в UI** | В Jaeger UI можно попасть только через oauth2-proxy с входом через корпоративный IdP (Keycloak/AD, OIDC) и MFA. Войти могут только сотрудники компании с актуальной учётной записью. Уволенный сотрудник теряет доступ автоматически, вместе с блокировкой в IdP |
| **Авторизация по ролям** | Доступ к Jaeger UI есть только у ролей **«Поддержка»**, **«Разработка»**, **«DevOps/SRE»** и у **архитектора**. Продавцы и операторы видят статусы заказов в CRM и MES, но не трейсы. Grafana — роли Viewer (бизнес-дашборды без ссылок на сырые данные) и Editor (инженеры). Административный доступ к Jaeger, Collector и OpenSearch — только у DevOps |
| **Минимизация данных** | В коде используется белый список атрибутов (раздел 2.5). Дополнительно в Collector: процессор `attributes`/`redaction` удаляет `http.request.header.authorization`, `cookie`, `user.email`, `user.phone`, `enduser.*`, значения параметров SQL. Маска по регулярным выражениям для email и телефонов в `exception.message`. Партнёры и сотрудники фигурируют только как внутренние ID |
| **Сетевая изоляция** | Collector, Jaeger и OpenSearch находятся во внутренней подсети без публичных IP. Группы безопасности: на порты OTLP Collector (4317/4318) — только ВМ приложений; к Jaeger Query — только oauth2-proxy; к OpenSearch — только Jaeger. oauth2-proxy доступен только из корпоративной сети или VPN |
| **Шифрование** | TLS везде: приложения → Collector (**mTLS**, у каждого сервиса свой клиентский сертификат), Collector → Jaeger, Jaeger → OpenSearch, браузер → oauth2-proxy. OpenSearch шифрует данные на диске (managed-сервис) |
| **Защита приёма** | mTLS не даёт отправлять спаны посторонним. Лимиты в Collector (`memory_limiter`, ограничение размера батча и числа атрибутов) защищают от засорения и DoS |
| **Внешний контекст** | В партнёрском API входящие `traceparent`, `tracestate` и `baggage` **не** используются как родитель и не распространяются дальше: начинается новый корневой трейс, а внешний `traceparent` (после проверки формата) сохраняется как ссылка. Так партнёр не может «подклеиться» к чужим трейсам или протащить данные в baggage. Партнёру возвращается только `X-Request-Id`, без внутренних деталей |
| **Аудит** | Журналы входа в Jaeger UI (oauth2-proxy) и обращений к OpenSearch собираются в централизованные логи (задание 4). Раз в квартал проверяется список пользователей с ролями доступа |
| **Хранение и удаление** | Ограниченный срок хранения (30 и 120 дней) с автоматическим удалением индексов. Резервные копии трейсов не нужны: это диагностические данные, а не учётные |
| **Секреты** | Сертификаты mTLS, учётные данные OpenSearch и OIDC-клиента хранятся в Yandex Lockbox (или Vault), а не в конфигурациях в Git |
| **Окружения** | Трейсы prod, release и dev хранятся раздельно (разные индексы или кластеры), доступ к prod — только у ролей выше. В dev и release тестовые данные без реальных ПДн |

Внешнего доступа к трейсингу (для партнёров) не предусматривается. Партнёры получают статус заказа через свой API и вебхуки (задание 1, I10), а не через Jaeger.
