## 1. Анализ системы: какие логи и откуда собирать

### Что происходит сейчас

- **Где лежат логи.** У каждого приложения один инстанс на отдельной ВМ. Логи, если они есть, лежат в файлах на этих ВМ в разных форматах (Java — Logback, C# — свой формат). Логи managed PostgreSQL доступны только в консоли облака.
- **Нет общего идентификатора.** Связать записи разных систем по одному заказу нечем: заказ партнёра «рождается» в MES API, а «появляется» (или не появляется) в CRM API.
- **Как идёт разбор.** Клиент описывает, что случилось. Разработчик заходит на несколько ВМ, ищет по времени и догадкам. Если ВМ перезапускалась или логи ротировались, данных уже нет.

### Из каких систем собираем логи

На [схеме 1](diagrams/01_logging_sources.drawio) системы-источники обведены красным, рядом стоит приоритет подключения (раздел 4).

| Система | Что даёт лог | Собираем | Приоритет |
|---|---|---|---|
| **MES API** (C#) | Приём заказов из очереди, расчёт стоимости (2–30 мин), партнёрский API, взятие в работу, статусы производства, публикация событий | Да | **P1** |
| **CRM API** (Spring Boot) | Подхват заказов из Shop DB, создание B2B-заказов из сообщений MES, подтверждение продавцом, приём статусов, запись в Shop DB, закрытие заказа | Да | **P1** |
| **RabbitMQ** | Соединения и отключения клиентов, отмена консьюмеров, memory/disk alarms, ошибки каналов, сообщения без маршрута | Да | **P1** |
| **Shop API** (Spring Boot) | Создание заказа, загрузка 3D-модели, оформление (SUBMITTED), ошибки для клиента | Да | **P2** |
| **Shop DB, MES DB** (Managed PostgreSQL) | Ошибки, медленные запросы (`log_min_duration_statement`), блокировки и deadlock, исчерпание соединений | Да, через Yandex Cloud Logging | **P2** |
| **3d files storage** (S3) | Журнал доступа к бакету: загрузка и чтение моделей, ошибки 4xx/5xx, размер объектов | Да | **P3** |
| **Internet Shop, CRM, MES** (фронтенды) | Ошибки JavaScript, неудачные загрузки файлов, ошибки 3D-редактора в браузере клиента | Только WARN/ERROR через API приёма клиентских ошибок | **P3** |

### Общий формат записи

Все приложения пишут **структурированные JSON-логи** с одинаковым набором полей. Это позволяет искать по полю, а не по тексту.

| Поле | Пример | Обязательно |
|---|---|---|
| `@timestamp` | `2024-11-14T10:42:17.123Z` (UTC, миллисекунды) | Да |
| `level` | `INFO` | Да |
| `service`, `service_version`, `env`, `host` | `mes-api`, `3.8.2`, `prod`, `mes-api-vm-1` | Да |
| `event` | `order.status_changed` (код события из каталога ниже) | Да для бизнес-событий |
| `message` | Короткий текст для человека | Да |
| `trace_id`, `span_id` | Из OpenTelemetry (задание 3) | Да, если есть контекст |
| `order_id` | `ORD-2024-118734` | Если операция связана с заказом |
| `customer_id` | Внутренний UUID покупателя, **не** email или телефон | Если известен |
| `partner_id`, `operator_id`, `seller_id` | Внутренние ID | По контексту |
| `request_id` | ID запроса (для партнёров совпадает с `X-Request-Id`) | Для HTTP |
| `duration_ms`, `result`, `error_code` | `1532`, `success` / `error`, `PRICING_TIMEOUT` | По контексту |
| `log_category` | `app`, `audit`, `access`, `security` | Да. По этому полю запись маршрутизируется в индекс |

### Список логов уровня INFO

INFO — это **значимые бизнес-события и смена состояния**, по которым можно восстановить, что происходило с заказом. Записи о каждом шаге внутри функции к ним не относятся. Кроме общих полей выше, у каждого события есть дополнительные поля.

#### MES API (P1)

| Событие (`event`) | Когда | Что логируем |
|---|---|---|
| `order.received` | Из очереди получен заказ на расчёт | Время, `order_id`, `customer_id` / `partner_id`, канал (`b2c` / `b2b`), `message_id`, задержка в очереди |
| `pricing.enqueued` | Задача расчёта поставлена в очередь | Время, `order_id`, хеш модели, размер файла, число полигонов, класс сложности, позиция в очереди |
| `pricing.started` | Начат расчёт | Время, `order_id`, ожидание в очереди (мс), номер попытки, инстанс |
| `pricing.completed` | Расчёт завершён | Время, `order_id`, длительность (мс), рассчитанная стоимость и валюта, класс сложности |
| `order.status_changed` | Любая смена статуса в MES: PRICE_CALCULATED, MANUFACTURING_STARTED, MANUFACTURING_COMPLETED, PACKAGING, SHIPPED | Время, `order_id`, `customer_id` / `partner_id`, старый и новый статус, кто изменил (`operator_id` или `system`) |
| `event.published` | Опубликовано сообщение в RabbitMQ | Время, `order_id`, тип события, exchange, routing key, `message_id`, подтверждение брокера (confirm) |
| `partner.request` | Запрос партнёра к API (access-лог, `log_category=access`) | Время, `partner_id`, метод, маршрут (шаблон), HTTP-код, длительность, `request_id`, IP, размер тела |
| `b2b.order.accepted` | Партнёрский заказ принят и отправлен на создание в CRM | Время, `order_id`, `partner_id`, внешний ID партнёра, `message_id` |
| `order.taken` | Оператор взял заказ в работу (`log_category=audit`) | Время, `order_id`, `operator_id`, сколько заказ ждал после подтверждения |
| `order.shipped` | Заказ передан в доставку | Время, `order_id`, `customer_id`, служба доставки, трек-номер |
| `app.started` / `app.stopped` | Старт и остановка сервиса | Время, версия, хеш конфигурации, причина остановки |

#### CRM API (P1)

| Событие | Когда | Что логируем |
|---|---|---|
| `order.picked_up` | Новый заказ SUBMITTED взят из Shop DB для отправки в MES | Время, `order_id`, `customer_id`, сколько заказ ждал после SUBMITTED |
| `event.published` | Опубликовано сообщение (новый заказ, MANUFACTURING_APPROVED, CLOSED) | Время, `order_id`, тип события, `message_id`, подтверждение брокера |
| `event.consumed` | Обработано сообщение от MES | Время, `order_id`, тип события, `message_id`, результат (`ack` / `requeue` / `dlq`), длительность обработки, задержка в очереди |
| `b2b.order.created` | Заказ партнёра создан в CRM по сообщению MES | Время, `order_id`, `partner_id`, внешний ID партнёра, `message_id` |
| `order.approved` | Продавец подтвердил заказ: MANUFACTURING_APPROVED (`audit`) | Время, `order_id`, `customer_id`, `seller_id`, сколько заказ ждал подтверждения |
| `order.status_changed` | Статус записан в Shop DB | Время, `order_id`, `customer_id`, старый и новый статус, источник (`mes` / `seller` / `carrier`) |
| `order.closed` | CLOSED: по сообщению транспортной компании или вручную (`audit`) | Время, `order_id`, `customer_id`, способ закрытия, `seller_id` при ручном закрытии |
| `order.updated_by_seller` | Продавец изменил данные заказа (`audit`) | Время, `order_id`, `seller_id`, список изменённых полей (без значений ПДн) |

#### Shop API (P2)

| Событие | Когда | Что логируем |
|---|---|---|
| `order.created` | Заказ заведён (INITIATED) | Время, `order_id`, `customer_id`, канал |
| `model.upload_started` / `model.uploaded` | Начата и завершена загрузка 3D-модели (FILE_UPLOADED) | Время, `order_id`, `customer_id`, размер файла, хеш, источник (`upload` / `constructor`), длительность загрузки в S3 |
| `order.submitted` | Пользователь нажал «Сделать заказ» (SUBMITTED) | Время, `order_id`, `customer_id`, число позиций |
| `order.status_viewed` | Клиент открыл статус заказа | Время, `order_id`, `customer_id`. Помогает понять, что клиент видел перед обращением |

#### RabbitMQ (P1)

| Событие | Что логируем |
|---|---|
| Подключение и отключение клиента | Время, имя соединения (`connection_name` = имя сервиса), пользователь, vhost, причина закрытия |
| Создание и отмена консьюмера | Время, очередь, тег консьюмера, причина |
| Alarms памяти и диска | Время, узел, тип alarm, порог |

Брокер пишет логи в JSON-формате (`log.file.formatter = json`).

#### PostgreSQL (P2)

| Событие | Что логируем |
|---|---|
| Медленные запросы | Запросы длительнее 1 с (`log_min_duration_statement = 1000`): время, БД, пользователь (`application_name` = сервис), длительность, текст запроса без значений параметров |
| Блокировки | Ожидание блокировки дольше `deadlock_timeout` (`log_lock_waits = on`), deadlock |
| Соединения | Отказы в подключении |

### Другие уровни логирования

| Уровень | Используем? | Когда | Примеры |
|---|---|---|---|
| **ERROR** | Да, всегда | Операция не выполнена, нужен разбор. Пишется со stacktrace, `error_code`, `order_id`, `trace_id` | Расчёт упал или превысил таймаут; сообщение ушло в DLQ после всех попыток; не удалось записать статус в Shop DB; ошибка S3 при загрузке модели; ответ 5xx партнёру; брокер не подтвердил публикацию |
| **WARN** | Да, всегда | Нештатная ситуация, которую система обработала сама, но которая может привести к проблеме | Повторная доставка сообщения (redelivered); повтор попытки расчёта; заказ в статусе дольше нормы; дубль запроса партнёра с тем же хешем модели; пул соединений почти исчерпан; медленный ответ дашборда (> 2 с); 429 партнёру; модель больше 100 МБ; ошибка валидации входных данных партнёра (4xx) |
| **INFO** | Да, всегда в prod | Бизнес-события и смена состояния (список выше) | — |
| **DEBUG** | Только **временно** в prod и постоянно в dev/release | Детали для разбора сложной проблемы. В prod включается на конкретный сервис и логгер через Spring Boot Actuator `/actuator/loggers` или динамический уровень Serilog, на ограниченное время (до 1 часа), по заявке в тикете. Хранится отдельно и 7 дней | Параметры расчёта, детали сопоставления статусов, тела сообщений RabbitMQ **с маскированием** |
| **TRACE** | Только dev | Пошаговая отладка | — |
| **FATAL / CRITICAL** | Да (Serilog `Fatal`, для Java — ERROR с маркером `FATAL`) | Сервис не может работать дальше | Не удалось подключиться к БД или брокеру при старте; неверная конфигурация |

**Правило.** Одно событие пишется на одном уровне один раз, без повторов на каждом слое кода. Ошибка логируется там, где её **обработали**, а не на каждом уровне стека.

## 2. Мотивация

### Проблема

- **Разбор начинается со слов клиента.** Клиент рассказывает, что «заказ пропал» или «файл не загрузился». Разработчику и поддержке приходится восстанавливать картину по памяти и косвенным признакам.
- **Расследование одной жалобы занимает часы или дни** и затрагивает нескольких человек: продавец, разработчик Java, разработчик C#, DevOps. При этом команда маленькая, и каждое такое расследование отнимает время у исправлений.
- **Часть данных теряется навсегда:** логи на ВМ ротируются и пропадают при пересоздании. Логов managed PostgreSQL никто не смотрит.
- **Проблемы находит клиент.** Компания уже теряет крупные контракты из-за заказов, о которых она узнаёт последней.

### Что даст логирование

| Для кого | Эффект |
|---|---|
| **Поддержка и продажи** | Поиск по номеру заказа (или ID партнёра) в одном окне. Видна история: создан, загружен файл, рассчитан, подтверждён, взят в работу, где ошибка. Многие обращения закрываются **без разработчика** |
| **Разработчики** | Все логи всех систем в одном месте, связанные по `order_id` и `trace_id`. Переход от трейса (задание 3) к логам и обратно. Stacktrace ошибки рядом с бизнес-контекстом |
| **B2B-партнёры** | Быстрый и точный ответ по конкретному запросу (`X-Request-Id`). Доказательная база при споре: запрос пришёл в 10:42, ответили 400 из-за неверного формата |
| **Руководство** | Аудит действий с заказами: кто и когда подтвердил, взял в работу, закрыл. Данные для разбора спорных ситуаций с клиентами |
| **Безопасность** | Обнаружение аномалий: всплеск заказов, перебор API-ключей, DDoS. Расследование инцидентов |

### Метрики, на которые повлияет внедрение логирования

| № | Метрика | Тип | Как измеряем | Ожидаемый эффект |
|---|---|---|---|---|
| 1 | **Среднее время разбора обращения (MTTR)** — от жалобы до найденной причины | Техническая | Время в тикете от создания до «причина установлена» | С часов или дней до 15–30 минут |
| 2 | **Доля обращений, закрытых первой линией** без эскалации на разработчиков | Бизнес и операционная | Число эскалированных тикетов к общему числу | Рост. Например, с ~10% до 50–60%: поддержка сама видит историю заказа |
| 3 | **Время разработчиков на разбор инцидентов** (часы в неделю) | Техническая и затраты | Учёт времени в задачах категории «инцидент» | Снижение. Освободившееся время идёт на инициативы задания 1 |
| 4 | **Время обнаружения проблемы (MTTD)** — от первой ошибки до реакции | Техническая | Время между первой записью ERROR и созданием инцидента | С дней (по жалобе) до минут (по алерту из логов) |
| 5 | **Число повторных обращений по одной проблеме** и **удовлетворённость клиентов и партнёров** (CSAT) | Бизнес | CRM и опросы после закрытия обращения | Снижение повторных обращений, рост CSAT. Меньше риск потери контрактов |

### Что подключать в первую очередь (логирование и трейсинг)

Подключить всё одновременно команда не сможет: один DevOps, один C#-разработчик. Поэтому порядок выбран по **ущербу от проблемы** и **затратам на подключение**.

| Приоритет | Системы | Логирование | Трейсинг | Почему именно так |
|---|---|---|---|---|
| **P1** (первые 3–4 недели) | **MES API, CRM API, RabbitMQ** | Да | Да (RabbitMQ — через заголовки сообщений) | **Самый большой ущерб.** Именно на стыке MES ↔ RabbitMQ ↔ CRM теряются заказы партнёров: «партнёры не получили заказ», потерянные контракты. MES API — самый нагруженный сервис: расчёт 2–30 мин, медленный дашборд операторов, партнёрский API. Без логов и трейсов этих трёх систем невозможно ответить, где пропал заказ. Логи RabbitMQ почти бесплатны: включить JSON-формат и поставить агент. CRM API подключается OTel-агентом за дни. MES требует больше работы, поэтому начинаем его параллельно |
| **P2** (следующие 2–3 недели) | **Shop API, Shop DB, MES DB** | Да | Shop API — да; БД — через клиентские спаны | Жалобы клиентов B2C растут, но часть их пути видна в Яндекс Метрике. Логи БД объясняют медленный дашборд (MES DB) и блокировки при общей записи Shop API и CRM API в Shop DB. Подключение стоит недорого: агент OTel для Java, настройка параметров логирования managed PostgreSQL |
| **P3** (после стабилизации) | **S3, фронтенды** | Журнал доступа S3, ошибки браузера (WARN/ERROR) | Фронтенды — опционально (OTel Web) | Полезно для разбора проблем с загрузкой моделей и 3D-редактором. Но это реже и дешевле по ущербу, а данные шумные и объёмные |

Это согласуется с планом трейсинга из [задания 3](../Task3/Архитектурное%20решение%20по%20трейсингу.md). CRM API подключается раньше всех, потому что это быстро (агент). Сразу за ним идут MES API и брокер: там основной ущерб.

### 3.1. Технологии и поток данных

```
 Shop API / CRM API (Logback JSON) ─┐
 MES API (Serilog JSON) ────────────┤  файл на ВМ   ┌─────────────┐   TLS, bulk   ┌──────────────────────────┐
 RabbitMQ (JSON-логи брокера) ──────┼──────────────►│ Fluent Bit  ├──────────────►│ Yandex Managed OpenSearch │
 /api/client-errors (фронтенды) ────┘               │ на каждой ВМ│               │  data streams, ISM, RBAC  │
                                                    └─────────────┘               └────────────┬─────────────┘
 Managed PostgreSQL ──► Yandex Cloud Logging ──► Log Importer (Cloud Functions) ──► bulk ──────┤
 S3: журнал доступа в бакет логов ────────────────► Log Importer ──────────────────────────────┤
                                                                                               ▼
                                     OpenSearch Dashboards (SSO) · Alerting · Anomaly Detection ──► каналы оповещений
```

| Компонент | Технология | Новый / доработка | Назначение |
|---|---|---|---|

### 3.2. Что нужно доработать в сервисах

1. **Shop API, CRM API:** заменить формат логов на JSON (logstash-encoder). Фильтр (servlet filter или аспект) кладёт `order_id`, `customer_id`, `request_id` в MDC. Добавить события из каталога (раздел 1). Перевести вывод в файл с ротацией (`/var/log/<service>/app.json`).
2. **MES API:** подключить Serilog с JSON-форматом и enricher контекста. Добавить события расчёта, партнёрского API (access-лог middleware) и публикации и обработки сообщений.
3. **Все сервисы:** вынести access-логи HTTP (`log_category=access`) отдельно от прикладных. Аудит-события (`log_category=audit`) — отдельной категорией.
4. **RabbitMQ:** включить JSON-формат логов. Задать `connection_name` в клиентах всех сервисов: тогда в логах брокера видно, какой сервис отключился.
5. **Managed PostgreSQL:** настроить параметры логирования, включить выгрузку в Cloud Logging, задать `application_name` в строках подключения сервисов.
6. **S3:** включить журнал доступа (server access logging) бакета 3D-моделей в отдельный бакет логов.

### 3.3. Политика безопасности логов

#### Работа с чувствительными данными

Принцип — **«не пишем то, что нельзя показать поддержке»**. Логи нужны для разбора, а не для хранения персональных данных. 152-ФЗ требует минимизации обработки ПДн.

| Категория данных | Правило |
|---|---|
| ФИО, телефон, email, адрес доставки | **Не логируются.** Вместо них внутренний `customer_id` (UUID). Чтобы узнать контакт клиента, поддержка открывает CRM, где уже есть права доступа и аудит |
| Пароли, токены, API-ключи партнёров, cookie, заголовок `Authorization` | **Никогда не логируются.** Маскирование в коде + фильтр Fluent Bit + алерт на появление в логах шаблонов, похожих на токен |
| Платёжные данные | Не логируются, онлайн-магазин их не обрабатывает. Если появятся, то только последние 4 цифры |
| Тела запросов и сообщений | Не логируются на INFO. На DEBUG — только с маскированием полей по белому списку |
| Содержимое 3D-моделей и исходные имена файлов | Не логируются. Логируются хеш, размер и число полигонов. 3D-модель клиента — его интеллектуальная собственность |
| IP-адреса | Только в access-логах и логах безопасности, которые хранятся отдельно и с ограниченным доступом |
| Данные партнёров | Логируется `partner_id`, а не название компании. Коммерческие условия (цены по договору) не логируются |

**Три линии защиты:**
1. **Код:** белый список полей и аннотации маскирования.
2. **Агент:** фильтр Fluent Bit с регулярными выражениями для email, телефонов и токенов.
3. **Хранилище:** монитор в OpenSearch, который ищет совпадения с шаблонами ПДн и создаёт инцидент ИБ. Найденное удаляется, источник исправляется.

#### Кто имеет доступ

Доступ к OpenSearch Dashboards — только через корпоративный IdP с MFA и только для сотрудников с актуальной учётной записью. Права выдаются ролями плагина Security OpenSearch: доступ к индексам, а также к отдельным документам и полям (document- и field-level security).

| Роль | Кто | Доступ |
|---|---|---|
| `support` | Поддержка, руководители продаж | Только чтение `logs-prod-*` (прикладные) и `audit-prod-orders`. Поля `client.ip`, `user_agent`, `exception.stacktrace` скрыты (field-level security). Нет доступа к `security-*`, `access-*` и к dev/release |
| `developer` | Разработчики | Чтение всех прикладных индексов всех окружений, включая stacktrace. В prod — только чтение. Нет доступа к `security-*` |
| `devops` | DevOps/SRE | Администрирование кластера, политик ISM, пайплайнов. Чтение всех индексов |
| `security` | Ответственный за ИБ (при найме или по совместительству — тимлид) | Чтение `security-*`, `access-*`, `audit-*`, журнала аудита самого OpenSearch |
| `architect`, `teamlead` | Архитектор, тимлид | Чтение прикладных и аудит-индексов, дашборды |
| Сервисные учётные записи | Fluent Bit на каждой ВМ, Log Importer | **Только запись** в свои data streams (`logs-prod-mes-api` и т. д.), без чтения |

Дополнительно:
- **Сетевая изоляция:** кластер OpenSearch без публичного IP. Доступ к API — только с ВМ приложений и Log Importer (группы безопасности). Dashboards — только из корпоративной сети или VPN.
- **Шифрование:** TLS между агентами и кластером, шифрование дисков managed-кластера.
- **Аудит доступа к логам:** журнал аудита OpenSearch (кто что искал и открывал) пишется в `security-prod-audit` и хранится 1 год.
- **Неизменяемость аудит-логов:** у индексов `audit-*` после ротации включается `index.blocks.write`. Удаление разрешено только политике ISM, у пользователей права на удаление нет.
- **Секреты:** пароли и сертификаты агентов хранятся в Yandex Lockbox, а не в конфигурациях.
- **Ежеквартальный пересмотр** состава ролей, мгновенный отзыв доступа при увольнении через IdP.

### 3.4. Политика хранения

#### Индексы

Используются **data streams** с ежедневной ротацией (rollover по возрасту 1 день или по размеру 30 ГБ на primary shard). **Отдельный поток на каждую систему и окружение** и отдельные потоки для аудита и безопасности. Так у каждой системы свои права и свой срок хранения, а «шумная» система не влияет на остальные.

| Data stream | Содержимое | Срок хранения в prod | Почему такой срок |
|---|---|---|---|
| `logs-prod-mes-api`, `logs-prod-crm-api`, `logs-prod-shop-api` | Прикладные логи INFO / WARN / ERROR | **30 дней** | Типичная жалоба поступает в течение 1–3 недель, этого достаточно для разбора |
| `logs-prod-<service>-debug` | Временно включённый DEBUG | **7 дней** | Нужен только на время разбора |
| `errors-prod` | Копия всех WARN и ERROR всех сервисов | **90 дней** | Анализ трендов ошибок, сравнение релизов, редкие инциденты |
| `access-prod-partner-api` | Access-логи партнёрского API | **90 дней** | Споры по SLA с партнёрами, анализ нагрузки по партнёрам |
| `access-prod-http` | Access-логи остальных API | **30 дней** | Разбор инцидентов |
| `logs-prod-rabbitmq` | Логи брокера | **30 дней** | Разбор инцидентов |
| `logs-prod-postgres` | Ошибки, медленные запросы, блокировки | **30 дней** | Оптимизация запросов (дашборд MES) |
| `logs-prod-s3-access` | Журнал доступа к бакету моделей | **30 дней** | Разбор проблем с загрузкой |
| `logs-prod-frontend` | Ошибки браузера | **14 дней** | Объёмные и шумные данные |
| `audit-prod-orders` | Аудит-события заказа (смены статуса, подтверждение, взятие в работу, закрытие, изменения продавцом) | **90 дней в кластере + 3 года в снимках** (snapshot в Object Storage, холодное хранение) | Заказ живёт до нескольких месяцев. Срок исковой давности по спорам с клиентами и партнёрами — 3 года (ГК РФ, ст. 196) |
| `security-prod-*` | Логи безопасности, аудит доступа к логам | **1 год** | Расследование инцидентов ИБ |
| `logs-release-*` | Все логи release | **14 дней** | Тестирование релиза |
| `logs-dev-*` | Все логи dev | **7 дней** | Отладка |

Жизненный цикл (политика ISM):
1. **hot:** запись и активный поиск, 1 реплика.
2. Через 7 дней: **force_merge** и только чтение.
3. По истечении срока: **delete**. Для `audit-*` перед удалением делается snapshot.

Резервные копии кластера — ежедневные snapshots в Object Storage (это средство managed-сервиса).

#### Оценка объёма

Исходные допущения:
- около 3 000 заказов в месяц сейчас, плюс 100 заказов каждый месяц;
- около 50 бизнес-событий на заказ;
- средний размер JSON-записи 0,6 КБ;
- поток HTTP-запросов оценён по числу операторов, продавцов и партнёров.

| Источник | Записей в сутки | Объём в сутки (сырые данные) |
|---|---|---|
| MES API: access-логи партнёрского API | ~100 000 | ~60 МБ |
| MES API: дашборд операторов (~60 операторов) + прикладные события | ~60 000 | ~40 МБ |
| CRM API | ~30 000 | ~20 МБ |
| Shop API | ~60 000 | ~35 МБ |
| RabbitMQ, PostgreSQL, S3, фронтенд | ~50 000 | ~30 МБ |
| **Итого** | **~300 000** | **~185 МБ (~5,5 ГБ в месяц)** |

С учётом индексов (×1,3) и одной реплики (×2) получается примерно **15 ГБ в месяц** в кластере. При сроках хранения из таблицы (в основном 30 дней, ошибки и партнёрский API — 90) в prod одновременно хранится **около 30–40 ГБ**. Сюда же идут трейсы из задания 3: около 10–20 ГБ.

**Размер кластера на старте:** 3 узла, у каждого 2 vCPU, 8 ГБ RAM и 100 ГБ SSD. Это 300 ГБ с запасом примерно ×4 на рост нагрузки, на временный DEBUG и на всплески, например при DDoS. Пересматривается раз в квартал по фактическому объёму: метрика размера индексов есть в мониторинге из задания 2.

**Ограничение объёма:**
- лимит размера записи 32 КБ (stacktrace обрезается);
- health-check и `/metrics` отбрасываются на агенте;
- если поток логов одного сервиса превышает норму в 10 раз, агент применяет throttling, а алерт уходит DevOps.

### 3.5. От сбора логов к анализу логов

Само хранилище логов полезно только при ручном поиске. Чтобы логи работали сами, нужны четыре вещи.

#### А. Алертинг (плагин Alerting OpenSearch → Notifications → мессенджер дежурных, тикеты, Alertmanager из задания 2)

| Монитор | Условие | Уровень | Реакция |
|---|---|---|---|
| Сообщение в DLQ | Запись `event.consumed` с `result=dlq` | critical | Дежурный. В уведомлении `order_id`, `message_id`, ссылка на трейс |
| Заказ партнёра не создан | `b2b.order.accepted` в MES без `b2b.order.created` в CRM с тем же `order_id` за 10 мин (bucket-level монитор) | critical | Дежурный + аккаунт-менеджер партнёра |
| Всплеск ошибок сервиса | Число ERROR сервиса за 5 мин больше 3× среднего за неделю и больше 20 | critical | Дежурный |
| Падение расчёта | `pricing.*` с `result=error` больше 3 за 15 мин | warning | Тикет команде MES |
| Сервис перестал писать логи | Нет записей от `service` дольше 10 мин в рабочее время | critical | Дежурный: сервис или агент упал |
| Отключение консьюмера | Лог RabbitMQ «consumer cancelled» или закрытие соединения сервиса без последующего подключения за 2 мин | critical | Дежурный |
| Ошибки партнёрского API | Доля 5xx для одного `partner_id` больше 5% за 10 мин | warning | Тикет и аккаунт-менеджер |
| Подозрение на ПДн или токен в логах | Совпадение с шаблонами email, телефона или токена | warning | Инцидент ИБ |
| Ошибки PostgreSQL | deadlock, `too many connections` | critical | Дежурный |

Метрики и алерты из задания 2 отвечают на вопрос «что сломалось по цифрам». Алерты по логам отвечают на вопрос «**какое именно событие** произошло» и сразу дают `order_id` и `trace_id`.

#### Б. Поиск аномалий (плагин Anomaly Detection OpenSearch, алгоритм Random Cut Forest)

Детекторы обучаются на исторических данных: 2–4 недели после запуска. Они учитывают суточную и недельную сезонность, поэтому порог не нужно подбирать вручную.

| Детектор | Признак | Что может значить | Реакция |
|---|---|---|---|
| **Всплеск создания заказов** | Число `order.created`, `b2b.order.accepted`, `pricing.enqueued` в минуту, в разрезе `partner_id` и канала | Пример из задания: было 4 заказа, стало 10 000 в секунду. Это DDoS, ошибка интеграции партнёра (цикл повторов) или злоупотребление расчётом цены | Critical. Автоматически: включить ограничение скорости для `partner_id` или IP (лимиты API Gateway / L7-балансировщика, Yandex Smart Web Security), временно заблокировать API-ключ при подтверждении. Дежурный и аккаунт-менеджер. Расчёты от аномального источника — в отдельную очередь с низким приоритетом, чтобы не задерживать остальные заказы |
| **Всплеск 401 и 403** | Число ответов 401/403 в минуту по IP и `partner_id` | Перебор API-ключей, утечка ключа | Блокировка IP, инцидент ИБ, перевыпуск ключа партнёру |
| **Аномальная длительность расчёта** | p95 `duration_ms` у `pricing.completed` по классу сложности | Деградация MES, нехватка ресурсов | Тикет, сигнал к масштабированию |
| **Аномальные размеры файлов** | Размер загружаемых моделей | Атака на хранилище, ошибочные загрузки | Ограничение на загрузку, проверка |
| **Падение потока событий** | Число `order.status_changed` в час ниже ожидаемого | Сломан консьюмер, что-то остановилось | Дежурный |
| **Новые типы ошибок** | Появление ранее не встречавшегося `error_code` или класса исключения после релиза | Регрессия | Тикет с привязкой к версии, кандидат на откат |

#### В. Дашборды и сохранённые запросы

Дашборды в OpenSearch Dashboards:
- **«История заказа»** (для поддержки): поиск по `order_id` или внешнему ID партнёра. Хронология всех событий из всех систем, ошибки, ссылка на трейс в Jaeger.
- **«Партнёр»**: запросы, ошибки и задержки по `partner_id`. Используется в разговоре с партнёром.
- **«Ошибки по сервисам и релизам»**: топ `error_code`, сравнение до и после релиза.
- **«Интеграция RabbitMQ»**: опубликовано и обработано, DLQ, повторные доставки.

Сохранённые запросы для первой линии поддержки: «почему заказ не рассчитан», «почему заказ не появился в CRM», «почему не загрузился файл». Это runbook в виде готовых фильтров.

#### Г. Процессы

- Еженедельный разбор топ-10 ошибок и аномалий с владельцами сервисов.
- Каталог событий входит в Definition of Done: новая функциональность без событий из каталога не принимается.
- Шумные алерты исправляются или удаляются на еженедельном обзоре.
- После каждого инцидента — проверка: хватило ли логов. Если нет, добавляется событие в каталог.

## 4. Дополнительное задание: критерии выбора технологии

### Критерии

1. **Лицензия** — можно ли свободно использовать, в том числе модифицировать и использовать в облаке.
2. **Стоимость владения** — лицензии плюс инфраструктура плюс затраты на эксплуатацию.
3. **Доступность в России и хранение данных в РФ** — можно ли купить и получать обновления. Есть ли managed-сервис в Yandex Cloud, где уже работает вся инфраструктура компании. Хранятся ли ПДн в РФ (152-ФЗ).
4. **Возможности поиска и анализа** — полнотекстовый поиск, поиск по полям, агрегации, язык запросов.
5. **Встроенные алертинг и поиск аномалий** — нужно ли что-то докупать или разрабатывать.
6. **Безопасность** — RBAC, document- и field-level security, аудит доступа, SSO. Входит ли это в бесплатную версию.
7. **Масштабируемость и стоимость хранения при росте**.
8. **Интеграция с остальным стеком** — трейсинг (Jaeger, задание 3), Grafana и Prometheus (задание 2), агенты (Fluent Bit, OpenTelemetry).
9. **Сложность эксплуатации для текущей команды** — один DevOps-инженер.

### Плюсы и минусы выбранного решения

**Выбор — Yandex Managed Service for OpenSearch + OpenSearch Dashboards + Fluent Bit.**

Плюсы:
- Свободная лицензия Apache 2.0, без риска лицензионных ограничений.
- **Все нужные функции бесплатны:** безопасность на уровне полей и документов (скрыть stacktrace и IP от поддержки), алертинг, поиск аномалий (DDoS-сценарий из задания), аудит доступа, SSO.
- **Managed-сервис в том же облаке:** данные в РФ, нет отдельной эксплуатации кластера. Это критично при одном DevOps-инженере.
- **Один кластер для логов и трейсов** (Jaeger из задания 3): единые права, один переход от трейса к логам по `trace_id`, меньше компонентов.
- Полнотекстовый поиск и агрегации нужны для поддержки: «найти все записи по заказу», «топ ошибок».

Минусы и как их компенсируем:
- **Дороже Loki и Cloud Logging на больших объёмах**, потому что индексируются все поля. При текущих 15 ГБ в месяц это несущественно. При росте в 10 раз и больше можно вынести access-логи и DEBUG в Loki или в Object Storage, а в OpenSearch оставить бизнес-события и ошибки.
- **Нужно проектировать индексы, шарды и ISM.** Это делается один раз (раздел 3.4), проверяется ежеквартально.
- **Отстаёт от Elastic по некоторым новым функциям.** Для наших задач это не критично.
- **Привязка к Yandex Cloud** для managed-варианта. OpenSearch — open source, при необходимости переносится на свои ВМ без изменения формата логов и агентов.

Почему не другие:
- **ELK:** платные функции безопасности и ML, нет поддержки и подписок в РФ.
- **Splunk:** ушёл из РФ, очень дорого.
- **Loki:** слабый полнотекстовый поиск и нет поиска аномалий. Остаётся кандидатом для дешёвого долгого хранения access-логов.
- **Cloud Logging:** используем как промежуточный приёмник логов managed PostgreSQL, но для анализа его возможностей поиска, маскирования и аномалий недостаточно.
